# slack-issue-intake

## 概要

Slack のワークフローのフォームから GitHub Issue を起票する Claude Code プラグインです。常駐サーバーは不要です。受け付けるリポジトリは複数の organization にまたがって登録できます。既定の起票先と、リポジトリごとのフォームへの表示・既存 Issue の扱いを設定します。

フォームはカテゴリごとに 4 つあり、チャンネルの入力欄の所にボタンが並びます。押したボタンでカテゴリが決まり、カテゴリに合った項目だけを聞きます。「質問する」は Issue を作らず、AI がスレッドで答えます（下の「質問する」）。

| ボタン | カテゴリ別の項目 | 共通の項目 |
|---|---|---|
| バグを報告 | 事象（必須・複数行）、エラーログ（任意・複数行）、対応策（任意・複数行）、画面のURL（任意）、ソースコードのパス（任意） | タイトル（必須）、優先度（必須）、添付ファイル（任意） |
| 要望を送る | 現在（必須・複数行）、理想（必須・複数行）、画面のURL（任意）、ソースコードのパス（任意） | 同上 |
| 新機能を提案 | 仕様（必須・複数行） | 同上 |
| 質問する | 質問の種類（必須・選択: 仕様について / バグか仕様なのかわからない / その他）、本文（必須・複数行） | 添付ファイル（任意）。タイトルと優先度は聞きません |

チャンネルへの投稿は、項目名を太字にし、複数行の値をコードブロックで囲みます。任意の複数行の項目（エラーログ・対応策）は、空のまま送ると「記載なし」と出ます（Slack の送る文面の型は空の値を出し分けられず、空だと囲みの ``` だけが残るため、フォームの既定値で埋めています）。「記載なし」は Issue の本文には入れません。0.2 までの 1 つのフォーム（`本文:` の形）の投稿も、そのまま読み取ります。

### 複数リポジトリとフォーム

`init --repo acme/app --repo other/api --default-repo acme/app` のように一覧を指定します。フォームに出す起票先が2つ以上なら、4つのフォームそれぞれに任意の「リポジトリ」欄が付きます。空欄なら既定の起票先へ送り、未登録の値は不備として返信します。`--hide-form <repo>` で選択肢を隠せますが、既定の起票先は常に表示されるため、既定を渡しても効きません。

### 向き先（作業を始めるブランチ）

リポジトリごとに向き先の候補（`develop` と `main` など）を設定すると、「質問する」以外の 3 つのフォームに任意の「向き先」欄が付きます。選択肢は `おまかせ` と候補のブランチです。欄が付くのは、フォームに出す起票先のどれかに候補が 2 つ以上あるときだけです。候補が無ければフォームは今までと同じです。

- `おまかせ` 以外を選ぶと、起票した Issue に `base:<ブランチ>` のラベル（例: `base:main`）を付けます。orca-team-dispatch-task はこのラベルを見て、そのブランチから作業を始めます。`おまかせ` や空欄なら付けず、向き先は orca-team-dispatch-task が決めます。
- 選んだリポジトリ（選ばなければ既定の起票先）の候補に無いブランチは、`おまかせ` とみなします。
- ラベルはリポジトリに無ければ起票の直前に作ります。作れなかったときは、ラベルを付けずに起票し、理由を poll と apply の出力に残します。選んだ向き先は Issue の本文の表（「向き先」の行）にも書くので、ラベルが付かなくても残ります。
- `base:*` はステータスラベルではありません。`make setup <名前>` の 5 段目の作り直しの判断（ラベルの指紋）には関わりません。
- 「質問する」には欄を付けません。質問から起票する Issue は `おまかせ` です。
- 候補は `make setup <名前>` の 4 段目で決めます（下の「聞かれること」）。手で設定するときは `init --branches acme/app=develop,main` をリポジトリごとに付けます。候補は orca-team-dispatch-task の設定とは別に持つので、両方の setup で同じ候補を入れてください。
- 候補を変えるとフォームのマニフェストが変わるので、次の `make setup <名前>` で deploy し直します。

### 質問する

「質問する」の投稿は Issue にせず、AI が投稿のスレッドで答えます。

- AI は、そのリポジトリの仕様の索引（下の「仕様の索引」）と、これまでに答えた質問（FAQ）を読んで答えます。根拠にしたドキュメントは、索引を作ったときの commit の GitHub のリンクとして回答の末尾に並びます。
- 索引に答えが無いときは、推測で答えずに「ドキュメントに見つからなかった」と答え、6 段目で決めたグループにメンションします。
- 質問者がスレッドに返信すると、次の回で AI がまた答えます。お礼だけの返信なら、短い締めの文で閉じます。回答は 3 回までで、上限に達したらグループにメンションして人へ渡し、閉じます。
- 返信が無いまま 72 時間たった質問は、何も書かずに閉じます（Claude は起動しません）。
- 質問の種類が「バグか仕様なのかわからない」で、AI がバグの可能性が高いと判断したときは、回答に「起票してほしい場合は、このスレッドにそう返信してください」を足します。質問者がそう返信したときだけ、AI が題を決めて Issue を作ります（カテゴリはバグ、優先度は `priority: middle`）。そのあとのステータスの通知はほかの Issue と同じです。
- 回答を投稿できたら、質問と回答を FAQ（`faq.jsonl`）に足し、次からの回答に使います。

#### 仕様の索引

索引はホームの下の `~/.slack-issue-intake-<名前>/knowledge/<owner>/<repo>/` に置きます（どのリポジトリにも commit されません）。

| ファイル | 中身 |
|---|---|
| `INDEX.md` | AI がまとめた全体像、話題とファイルの対応、用語集、各ドキュメントの要約 |
| `index.json` | `INDEX.md` の元のデータ（検査したあとの値） |
| `docs/` | ドキュメントの写し（リポジトリ内と同じパス） |
| `meta.json` | 作ったときの commit・日時・写したファイル |
| `faq.jsonl` | 答えた質問と回答。作り直しでは消しません。500 件を超えたら古い順に捨てます |

作るのは人がいるときだけです。`make setup <名前>` の 8 段目（索引がまだ無いリポジトリがあるとき）、`make slack-form <名前>` の始め、`make knowledge <名前>`（索引だけを作り直す）で作ります。

1. `gh repo clone <owner/name> -- --depth 1` で一時ディレクトリに取ります（gh の認証を使います）。
2. `claude -p` を読み取りだけ（`--tools Read,Glob,Grep`、`--permission-mode dontAsk`、`--strict-mcp-config`、clone の中で実行）で動かし、索引の JSON を作らせます。
3. AI が挙げたファイルのうち、clone の中の通常のファイル（symlink でない）で、拡張子が md / mdx / txt / rst / adoc のものだけを写します。1 ファイル 200KB、合計 5MB、200 件までです。外れたものは `dropped` の行で知らせて捨てます。写すときと索引の文字列は、トークンらしい文字列を伏せます。
4. 古い `docs/` との入れ替えは、新しい版を全部書けたあとに行います。途中で失敗したら前の版が残ります。clone はいつも消します。

作れなかったリポジトリがあっても、setup と slack-form は止まりません。そのリポジトリの質問には「ドキュメントに見つからなかった」と答えます。索引の作成日が 30 日より古いと、AI には古いと伝えます。

無人の Claude に新しく許すのは、この索引のディレクトリの読み取り（`Read(/<ホーム>/knowledge/**)`）だけです。リポジトリそのもの（`.env` などを含む）は読ませません。索引の中身も、投稿と同じく信頼しない材料として扱わせます。

### スレッドで管理する Issue

`--existing <repo>=thread` にしたリポジトリでは、Slack から作っていない Issue に管理用のトップレベル投稿を作り、`slack-thread` を付けます。既定の `skip` は対象外です。古い Issue はステータスラベルが付いたものだけ、設定後に作られたものはラベルなしでも管理します。フォームからの起票には `from-slack` が付きます。

`--existing <repo>=active` にしたリポジトリでは、開始時刻に関係なく、`Backlog` 以外のステータスラベルが付いた Issue（`Backlog` と別のステータスが両方付いたものを含む）と、人が `slack-thread` を付けた Issue（DB に行が無いもの）を管理します。ステータスなしや `Backlog` だけの Issue、`from-slack` の Issue、PR は対象外です。Project で Ready にした手作りの Issue は、orca-team-dispatch-task の同期でステータスラベルが付いてから取り込まれます。1 つのリポジトリを `active` にするのは 1 つのホーム（intake）だけにしてください。thread から active に切り替えると、thread のあいだに intake が `slack-thread` を付けた Issue（古い Backlog のものも含む）が、人が付けた印として orca-team-dispatch-task の auto-ready の判定に回ります。AI に判定させたくない Issue は `slack-thread` を外すか、切り替える前に `autoReady` を切ってください。`init` は切り替えを見つけると警告を 1 行出します。1 つのリポジトリは 1 つのホームだけで扱い、ホームごとに thread と active を混ぜないでください。thread と書いた設定が 1 つでもあるリポジトリは、orca が active として扱いません。setup の質問には `y`（thread）/ `active` / `n`（skip）で答えます。

### 定期報告

orca-team-dispatch-task の `--auto` が書く報告の材料から、実行中の Issue、キュー、マシンを投稿します。報告はそのホームのリポジトリの Issue だけを出し、マシンは名前とつながるかだけを出します（ほかのワークスペースの作業が分かる数は出しません）。普段は同じ投稿を書き換え、ローカル時刻の既定09:00を過ぎた最初の poll で1日1回新しく投稿します。材料が間隔の3倍を超えて古くなると、`--auto` が止まっている旨を表示します。

### 判定の学びの知らせ

orca-team-dispatch-task の `--auto` が判定の学び（規則ができた・根拠が増えた・取り下げた・様子見を終えた・全体の改善の下書きができた・全体の改善の Issue や PR ができた）を報告の材料と同じフォルダの `learn/notices.json` に書くと、poll が定期報告のチャンネルへ 1 つずつトップレベルで投稿します（定期報告が無効なら投稿しません）。投稿するのはそのホームのリポジトリの知らせだけで、1 回の poll で 5 件までです。規則の文と根拠は Slack の記法を効かせずに出し、根拠は `#番号` で示します。

規則ができた・根拠が増えた知らせには、取り消しの案内が付きます。そのスレッドに「取り消し 1」のように番号を返信すると（チャンネルに書ける人なら誰でも）、poll がホームの `learn-cancels.json` に取り消しの依頼を書き、「取り消しを受け付けました」と返信します。orca-team-dispatch-task は次の確認でその規則を取り下げ、判定を元の基準に戻します。返信を読むのは新しい 20 件の投稿のうち、知らせから 14 日以内のスレッドだけです。受け付けの返信に失敗したときは、次の poll でその返信を読み直して受け付けを返します。既存 Issue の取り込みの時間を残すため、poll の残り時間が 10 秒を切ると、投稿と返信の読み取りを次の poll に回します。poll の結果には `learn=<投稿数>/<依頼数>`（依頼数は取り消しと公開の合計）が付きます。Claude は起動しません。

全体の改善の Issue（公開リポジトリ yui-cc-plugins に出す）は、すぐには作られません。orca-team-dispatch-task はまず下書きを知らせ、報告先のチャンネル（設定の `report.channel`）を設定していれば、poll はその題と本文の全文を投稿します（本文は 1 行ごとに「│」の印を付けて出します）。設定していないと投稿はフォームのチャンネルに落ちるので、下書きは題と本文を出さず、下書きがあることと端末での読み方・公開の仕方を述べた 1 行だけにし、そのスレッドへの「公開 1」「取り消し 1」は受け付けません（あとで設定しても、題と本文を出さずに投稿したスレッドでは同じです）。読んで問題が無ければ、そのスレッドに「公開 1」のように番号を返信してください。poll が `learn-cancels.json` に公開の依頼を書いて「公開を受け付けました。次の確認で Issue を作ります」と返し、orca-team-dispatch-task が次の確認で Issue を作ります。出さないなら「取り消し 1」と返信します（規則は残り、下書きだけを捨てます）。本文が長くて 1 つの投稿に収まらないときは、省いたことを示して短く出し、Slack からは公開できません。題や本文のトークンの形の文字列を伏せて出したとき・制御文字などを置き換えて出したときも同じです。公開を承認できるのは、定期報告のチャンネルに書ける人なら誰でもです。ただしボットや連携の投稿の「公開 1」は無視します（取り消しは今までどおり受け付けます）。依頼にはどれも、人が見た項目の中身のハッシュを残し、orca-team-dispatch-task はそれが自分の知らせと合うときだけ反映します。報告の材料の場所を変えたなどで、スレッドに投稿した知らせと今の知らせが違えば、そのスレッドの返信は受け付けません。公開の依頼には承認した人の Slack の user id を残し、orca-team-dispatch-task は Issue を作ったときの行にその id を出します（GitHub には送りません）。Slack から公開できない下書きは、orca-team-dispatch-task の `status` で全文を読み、`orca-auto.ts learn-publish` で公開してください。

orca-team-dispatch-task の `learn/` を作り直した、または `report.source` を別の名前の `--auto` に向けたときは、知らせの id が 1 から数え直しになります。poll は最後に投稿した知らせの id と投稿の記録をホームの `intake.db` の表 `meta` に持ち続ける（鍵 `learn_last_notice` と `learn_posts`）ので、新しい id が前の最大を超えるまで、学びの知らせは errors も出さずに投稿されません（`learn=0/0`）。すぐ投稿させるには、automation を止めて poll が動いていないときに、その 2 つの行を消してから automation を戻してください（例: `sqlite3 ~/.slack-issue-intake-<名前>/intake.db "DELETE FROM meta WHERE key IN ('learn_last_notice', 'learn_posts')"`）。次の poll から、今の `notices.json` にある知らせを id の小さい順に投稿します（`notices.json` は新しい 50 件まで。前のスレッドへの返信は読まなくなります）。

### ステータスの通知

起票した Issue には、ステータスラベル `Backlog` を付けます。ステータスが変わると、元の投稿のスレッドへ知らせます。ラベルは、Issue を自動で消化する orca-team-dispatch-task と共通です。

| ラベル | 付ける人 | 意味 |
|---|---|---|
| Backlog | このプラグイン（起票時） | 起票直後。人の判断待ち |
| Ready | 人（auto-ready なら AI） | やる。AI が拾う対象 |
| Pending | 人 | 後回し |
| Ready_Eng | AI | 重い・長い・新機能など。エンジニアが対応する |
| In progress | AI | AI が実装中 |
| In review | AI | PR を出して人の判断待ち |
| Testing | AI | merge 済み。人の動作確認待ち（Issue は既定では開いたまま） |
| Done | 人 | 動作確認まで済んで完了。Issue を閉じる |
| Failed | AI | AI が失敗した |

確認の間隔ごとの poll で すべてのリポジトリの `from-slack` と `slack-thread` の Issue を読み、前回からステータスか開閉が変わったものだけを書き込みます。Claude は起動しません。

| 変化 | スレッドへの書き込み | メンション |
|---|---|---|
| Ready（auto-ready で AI が判定） | 自動で対応すると判断したことと判定の理由 | なし |
| Ready_Eng（AI の判定） | エンジニアへの依頼と判定の理由 | あり |
| In review（AI） | 確認の依頼、PR、AI が決めた点 | あり |
| Testing（AI が merge した） | merge したことと動作確認の依頼、PR、変更の要約 | あり |
| Testing（人が merge した PR を AI が見つけた） | merge されたことと動作確認の依頼、向き先が普段と違うときは戻しの PR のリンク | あり |
| Done（人が変えた）、閉じた | 完了したこと | なし |
| Failed | 失敗したことと理由 | あり |
| 作業が進んでいない（AI のラベルは In progress のまま） | 経過時間と上限時間 | あり |
| 向き先のブランチを尋ねた（`needs-base`。ステータスは Backlog に戻るか Backlog のまま） | 向き先のブランチを尋ねたこと（付けるラベルの候補） | あり |
| それ以外の変化 | ステータスが変わったこと | なし |

- AI が変えたかどうかは、Issue のコメントの最終行のマーカー（`<!-- orca-auto:<status>:<世代>:<種類> -->`）で見分けます。
- マーカーを信じるのは、書いた人がリポジトリのオーナー・メンバー・コラボレーター（または起票に使う gh のアカウント）で、マーカーのステータスが今のラベルと一致するときだけです。それ以外は人が変えたものとして扱い、コメントは転載しません。
- orca-team-dispatch-task はコメントを書いてからラベルを動かします。ラベルが変わらないうちに合わないマーカーを読んだ回は、何も書かずに次の回へ回します。
- Done を付けるのと閉じるのが別の回に分かれても、完了は 1 回だけ書きます。
- merge のあとは Done ではなく Testing になり、動作確認を頼みます。確認が済んだら人が Done にして閉じます。Issue を merge と同時に閉じるかは orca-team-dispatch-task の設定（`--auto` は `closeOnMerge`、`--issue` は `close_on_merge`）で選べ、既定は閉じません。閉じる設定では Testing のまま閉じるので、あとで Done にしても完了は書きません（閉じた時点で完了とみなすため）。
- メンションするのは、`make setup <名前>` の 6 段目で入力したユーザーグループです。空のまま進めたときはメンションしません。あとから変えるときは `node bin/slack-issue-intake.ts --name <名前> mention --group <ハンドル>`（やめるときは `--none`）を実行します。
- この機能を入れる前からある Issue は、最初に見たときに今の状態を記録するだけで、知らせません。Backlog も付けません。
- ステータスラベルが 2 つ以上付いているときは、Done、Testing、Failed、In review、Ready_Eng、In progress、Pending、Ready、Backlog の順で先にあるものとみなします。
- Backlog から Ready への判断も AI に任せるときは、orca-team-dispatch-task の `make setup NAME=<name>` の 2 段目（拾う元）で auto-ready を使います。有効にした後に起票された Issue だけが対象で、自動で対応できるものは Ready、難しいものは Ready_Eng になります。auto-ready で Ready になった Issue の PR は、既定では In review で止まり、人が merge します。orca-team-dispatch-task の拾う元で `autoMerge` を有効にすると、ほかの条件がそろえば AI が merge します（普段の向き先以外へは merge しません）。

### Slack の返信を Issue に転記する

Issue のスレッドでボット（`@Issue Intake`）にメンションして返信すると、次の poll がその返信を Issue のコメントに転記し、スレッドに「Issue に転記しました: <コメントの URL>」と返します。動作確認の結果や追加の情報を Slack から Issue へ残すときに使います。Claude は起動しません。

- 転記するのは、このワークスペースの人がボットにメンションした返信だけです。メンションの無い返信、ボットや連携の投稿、ほかのワークスペースの人（Slack コネクトなど）の返信は転記しません。
- 対象は、このプラグインが結び付けた Issue（フォームから起票したものと、スレッドで管理する既存 Issue）のうち、開いているもののスレッドです。閉じた Issue のスレッドは読みません。
- コメントは起票に使う gh のアカウントで書き、先頭に Slack の投稿者名（Markdown の記号は効かせません）と元の投稿へのリンクを付けます。本文はコードブロックに入れ、秘密に見える文字列は伏せます。添付ファイルは件数だけ書きます（中身は元の投稿で見ます）。本文は 10,000 文字で切ります。
- 公開リポジトリでは、転記した返信も公開されます。
- この機能を入れる前の返信は転記しません。スレッドを初めて見た時点から後の返信が対象です。
- 1 回の poll で読むスレッドは 20 までで、しばらく読んでいないスレッドから順に読みます。開いている Issue が多いと、転記まで何回かの poll がかかります。
- 書いた応答が届かなかったときは、次の回に Issue のコメントの最終行の印（`<!-- slack-issue-intake-reply:<チャンネル>:<ts> -->`）を探し、あれば書き直しません。書けない返信は 5 回で諦めて次へ進みます。消されたスレッドは読まなくなります。
- orca-team-dispatch-task は、Issue を Ready に戻して次の世代を始めるとき、転記したコメントも続きの材料として読みます。

## 仕組み

```text
Slack のフォーム → チャンネル投稿
  ↓ N分ごと
Orca precheck: poll（モデルなし）
  ├─ 判断待ちなし → Claude を起動せず終了
  └─ 判断待ちあり → Claude: procedure → collect → 判断を decisions.json → apply
                                        ↓
                        必要ならスレッドで確認 → Issue 作成 → URL を返信
                        質問なら、仕様の索引をもとにスレッドで回答（Issue は作らない）
  └─ 時間が残っていれば（モデルなし）: Issue のステータスの変化 → スレッドへ通知
```

新規・返信済み・期限切れの判断だけに Claude を使い、質問の投稿・作成・通知の再試行は CLI が進めます。聞き返しは2回まで、各3問以内、回答待ちは72時間です。

## 必要なもの

- Slack の有料プランと、そこでアプリを作れる権限（アプリは社内向けのカスタムアプリで、配布しません）
- Slack CLI（公開版）。`slack login` でログイン済みであること。`make setup <名前>` で使います。使えない場合は「Slack CLI を使わないセットアップ」で進めます
- 同じ Mac の Node 24.15 以上
- 対象リポジトリの push 権限（WRITE 以上）があるアカウントで認証済みの GitHub CLI（gh）
- 起動中の Orca と Claude Code（仕様の索引を作るときに `claude` コマンドと `git` も使います）

### ワークスペースと名前

Slack のワークスペースごとに名前を付けます。名前は必須です。

```bash
make setup <名前>
```

- 名前は英小文字・数字・`-` の 1〜32 文字で、先頭は英小文字か数字です。`slack-app` と、`-slack-app` で終わる名前は使えません。
- make の setup・manifest・slack-form・knowledge は、名前（`make setup ws2` の `ws2`）が無ければ今ある名前を並べて端末で聞きます。質問は標準エラーに出すので、マニフェストを `pbcopy` へ渡しても混ざりません。入力が無ければ名前付きのコマンドを示し、終了コード 2 で止まります。
- ホームは `~/.slack-issue-intake-<名前>/`、Slack CLI のプロジェクトは `~/.slack-issue-intake-<名前>-slack-app/` です。トークン・設定・DB はワークスペースごとに分かれます。automation はこの PC にワークスペースごとに 1 つでき、名前は `slack-issue-intake-<名前>` です。
- ボタンの置き直しとマニフェストの表示も `make slack-form <名前>`・`make manifest <名前>` と同じ名前を付けます。CLI は `node bin/slack-issue-intake.ts --name <名前> status` のように、サブコマンドの前に `--name <名前>` を付けます。無ければ今ある名前と、名前を足したコマンドを示し、終了コード 2 で止まります。
- 設定・トークンが無いときは、確認したホームと、そのまま打てるコマンドを示します。
- 以前の版で名前なしで作った `~/.slack-issue-intake/` は setup では使わなくなりました。登録済みの automation（`slack-issue-intake`）は、そのホームのランチャーから今までどおり動きます。`make setup <名前>` で設定し直したら、Orca でその automation を止めてください。止めないと、同じチャンネルを 2 つの automation が読み、同じ投稿から Issue を 2 回作ることがあります。ディレクトリは消して構いません。setup は見つけると最初に 1 行で知らせます。
- orca-team-dispatch-task の `--auto` で全部のワークスペースの Issue を処理するときは、その `make setup <name>`（`--auto` の設定の名前。既定は `main`）の 2 段目（拾う元）で、ワークスペースごとのホームの config.json を全部選びます。
- `--auto` を使っている場合は、新しいワークスペースをキューに含めない場合も、追加後に orca-team-dispatch-task の `make setup <name>`（`--auto` の設定の名前。既定は `main`）をやり直し、12 段目で権限を承認し直してください。追加された秘密ファイルの拒否ルールで `--auto` の承認指紋が変わり、それまではランチャー経由の tick が止まります。

### 途中で止まったとき

もう一度 `make setup <名前>` を実行します。済んだ段は飛ばし、止まった段から再開します。

- アプリとトークンがそろっていれば、deploy はやり直しません。ただし、プラグインの更新でマニフェストが変わったときは、次の実行でもう一度 deploy します。
- 設定と automation が登録済みなら、チャンネルは聞きません。今の設定を表示し、足すリポジトリと確認の間隔を聞きます。間隔は今の値を既定にします。Enter ならそのまま、別の値を入れると init で automation を書き換えます（公開リポジトリなら、もう一度確認します）。
- Slack CLI のプロジェクト（`~/.slack-issue-intake-<名前>-slack-app/`）にアプリの記録が無いときは、2段目で既存のアプリ ID を聞きます。プロジェクトを消した、別の端末で作った、などのときは、そのアプリの ID（https://api.slack.com/apps の Basic Information）を入力すると、`slack app link` でつないで同じアプリを更新します。空のまま Enter を押すと、もう1つアプリができます。
- 設定は保存されたが automation の登録（Orca）で失敗していたときは、保存済みのチャンネルとリポジトリで init をやり直します。公開リポジトリなら、もう一度確認します。
- ボタンが作成済みで、おすすめワークフローにしてあれば、作り直しません。前の版で関連ページ（ブックマーク）に「Issue を起票」を足していた場合、それは押すとブラウザが開いてしまうので、Slack で手で削除してください。
- 一度答えたメンション先は聞き直しません（6段）。変えるときは `mention` を直接実行します。
- 権限が承認済みなら10段は飛ばし、11段では聞き直さずに enable をやり直します。前回 Orca での有効化に失敗していても、ここで有効になります。

終了コードは、失敗が 1、入力がないときが 2 です。

Slack CLI で作ったアプリが無く、`node bin/slack-issue-intake.ts --name <名前> set-token` でトークンだけ登録してある場合は、手作業で作ったアプリとして進みます。このときボタンは作らないので、9段で「Workflow Builder で手で作る」を案内します。

### 終わったあとの確かめ方

チャンネルの入力欄の所に出る 4 つのボタンのどれかを押してフォームを1件送り、数分後に次を実行します。

```bash
node bin/slack-issue-intake.ts --name <名前> inspect --raw
```

いま送った投稿の行に `marker=yes`、`parse=ok`、`reporter=U…`、添付の数と同じ `files=` が出ていれば完成です。このフォームの投稿はアプリ自身のボットが書くので、`bot=yes` と出ます。添付なしでも送れるかも試してください。

| `Slack に deploy 済みのアプリが、今のフォームの定義と違います` | プラグインを更新したあとに `make slack-form <名前>` だけを実行した場合です。`make setup <名前>` を実行して deploy し直してください。9 段目でボタンも置きます |
| `以前の 1 つのボタンは、新しいボタンが入力欄の所に出るまで残します` | ボットでは新しいボタンをおすすめにできなかったので、0.2 のボタンを残しています。画面で新しいボタンをすべて注目にしてから `make slack-form <名前>` をもう一度実行すると、古いボタンを外して消します |
| `以前の 1 つのボタン（…）を消せませんでした` | 新しいボタンは使えます。一時的な失敗なので、次に `make slack-form <名前>` か `make setup <名前>` を実行したときにもう一度消します。ボタンがもう無い場合は、消えたものとして扱います |
| 入力欄の所のボタンが消えた | 起票のチャンネルは setup の最後に出るリンクで開けます。起票のチャンネルの「ワークフロー」タブ →「ワークフローを目立たせる」で「バグを報告」「要望を送る」「新機能を提案」「質問する」の 4 つを選び、「注目」を押します。入力欄の所に 4 つのボタンが出ないときは、ブラウザで Slack の管理画面を開き、Admin →「Apps and workflows」→「Workflows」で 4 つのそれぞれ（アプリ Issue Intake）の詳細を開いて、右上のメニューから「おすすめアプリに追加」を選びます。`make slack-form <名前>` は記録済みなので付け直しません |
| `ユーザーグループの一覧を読む権限（usergroups:read）がありません` | 手作業で作ったアプリです。アプリの設定画面の OAuth & Permissions で `usergroups:read` を足してアプリを入れ直すか、グループ ID（S で始まる）を入力します |
| `ユーザーグループ「…」が見つかりません` | ハンドル（@ のあとの名前）か表示名を確かめます。Slack の無料プランなど、ユーザーグループが無いときは空のまま進めます |
| ステータスが変わってもスレッドに書き込まれない | `status` の直近の poll にエラーが出ていないかを見ます。取り込みに時間を使い切った回は、次の回で知らせます。この機能を入れる前からある Issue は、最初の 1 回は記録だけです |
| `… の仕様の索引を作れませんでした` | 括弧の中の理由を見ます。`claude` コマンドや `git` が無い、gh で clone できない、などです。直したら `make knowledge <名前>` で作り直します。作れるまで、そのリポジトリの質問には「ドキュメントに見つからなかった」と答えます |
| `inspect` で `parse=invalid` になる | `problems=` に、足りない項目や合わない選択肢が出ます。手で作った場合は、テンプレートと選択肢の文字を見直します |

### 0.2 からの更新

0.3 でフォームは 1 つからカテゴリごとの 3 つになりました。プラグインを更新したら `make setup <名前>` を実行します。

1. 2 段目で、3 つのワークフローを持つマニフェストを deploy し直します。
2. 7 段目で 3 つのボタンを作っておすすめにし、そのあとで 0.2 の 1 つのボタンを外して消します。チャンネルから新しいボタンが出る前に古いボタンを消すことはしません。
3. ボットでおすすめにできない環境では、古いボタンを残したまま先へ進みます。画面で 3 つを注目にしてから `make slack-form <名前>` を実行すると、古いボタンを片付けます。

deploy（2 段目）から 7 段目までの間、古いボタンは押しても動かないことがあります（Slack の実際の動きは未確認）。`make slack-form <名前>` だけを先に実行すると、deploy し直すよう案内して止まります。0.2 の形（`本文:`）で投稿済みのものは、そのまま読み取ります。

### 0.3 からの更新

0.4 で、ステータスの通知が入りました。プラグインを更新したら `make setup <名前>` を実行します。

1. 2 段目で、`usergroups:read` を足したマニフェストを deploy し直します。
2. 5 段目で init をやり直し、ステータスラベル 8 つを作ります。それまでの起票には Backlog を付けません（無いラベルを付けると起票が失敗するため）。
3. 6 段目で、メンションするグループを聞きます。

前からある `from-slack` の Issue には Backlog を付けません。最初の poll で今の状態を記録し、そのあとの変化から知らせます。手作業で作ったアプリは、アプリの設定画面で `usergroups:read` を足して入れ直してください（足さなくても、グループ ID を入力すれば使えます）。

### 0.15 からの更新（空欄の「記載なし」）

0.16.0 で、任意の複数行の項目を空のまま送ると、投稿に空の ``` ではなく「記載なし」と出るようにしました（フォームの既定値）。フォームが変わるので、`make setup <名前>` を実行してマニフェストを deploy し直します。手で作ったワークフローでは、エラーログと対応策の既定値に「記載なし」を入れます。Slack の文書は既定値の働き（空で送ったときの値か、入力欄に最初から入る文字か）を書いていません。入力欄に最初から入る形だった場合も、消し忘れた「記載なし」の行は Issue の本文から外します。

### 0.14 からの更新（返信の転記）

0.15.0 で、スレッドでボットにメンションした返信を Issue へ転記するようになりました。設定は要りません。更新後の最初の poll で開いている Issue のスレッドを記録し、それより後の返信から転記します。

### 0.13 からの更新

0.14.0 で、merge のあとのステータスに Testing が入りました（Done は人が動作確認してから付けます）。プラグインを更新したら `make setup <名前>` を実行します。5 段目で init をやり直し、Testing のラベルを作ります。それまでの起票には Backlog を付けません（ラベルの一覧が変わったため）。orca-team-dispatch-task の Project を使っているなら、Project の Status にも Testing の選択肢を足します（`make auto-setup` の Project の段が足します）。

### 0.4 からの更新

`make setup <名前>` でリポジトリの追加・既存 Issue の扱い・定期報告を設定します。選択肢が増えるとマニフェストを deploy し直してからフォームへ進みます。旧configはそのまま読め、旧DBの行は poll または init がリースの下で旧リポジトリに固定して移行します。既定の起票先を変えても、過去の Issue は元のリポジトリに残ります。

### 0.7.0 以前からの更新

0.7.1 で「質問する」のボタンと仕様の索引が入りました。プラグインを更新したら `make setup <名前>` をもう一度実行します。

1. 2 段目で、4 つ目のワークフローを足したマニフェストを deploy し直します。
2. 8 段目で、仕様の索引を作ります。
3. 9 段目で「質問する」のボタンを作り、4 つをおすすめにします（ボットでおすすめにできない環境では、画面で 4 つを注目にします）。

手作業で作ったアプリでは、「Workflow Builder で手で作る」で「質問する」のワークフローを足し、`node bin/slack-issue-intake.ts --name <名前> knowledge` で索引を作ってから、`permissions --apply` と `enable` をやり直します。

### 0.8.0 以前からの更新

0.9.0 でフォームの「向き先」欄が入りました。使うときは `make setup <名前>` をもう一度実行し、4 段目で既定の起票先の候補を答えます（ほかのリポジトリは `init --branches` で足します）。候補を入れると init をやり直し、マニフェストを deploy し直してから進みます。候補を入れなければ、フォームもマニフェストも今までと同じです。

### 送り先を変えたあとの片付け

リポジトリは追加できますが、管理中の Issue の通知を失わないよう削除できません。既定の起票先は登録済みの一覧から変更できます。

チャンネルを変える、またはリポジトリを削除して設定し直すには、automation を止め、ホームを退避して `make setup <名前>` をやり直します。同じアプリを使い続け、トークンは deploy で取り直します。古いチャンネルのボタンは自動では消えないので、手で片付けます。

1. `slack trigger list --app deployed` で古いボタンの ID（`Ft…`）を調べ、`slack trigger delete --trigger-id <ID> --app deployed` で消します。Slack CLI のプロジェクトは `~/.slack-issue-intake-<名前>-slack-app/` にあります。このディレクトリで実行します。
2. 古いチャンネルの「ワークフロー」タブで、4 つのワークフローそれぞれの 3 つのドットアイコン →「注目から外す」を選びます（トリガーを消していれば消えています）。

### 別のマシン・作り直したボットからの引き継ぎ（relink）

スレッドと Issue の結び付きは、ホームの `intake.db` にだけあります。次のときは、Slack にスレッドが残っていても、新しいホームはどの Issue がどのスレッドのものかを知りません。ステータスが変わってもスレッドに何も書かれず、poll は `notified=0` のままです。

- 別のマシンで動かしていた intake を、`intake.db` を持ってこずに新しいマシンで `make setup <名前>` し直した
- `intake.db` を消した・壊した

`relink` は起票のチャンネルの履歴を読み、このプラグインが前に作ったスレッドを探して結び付け直します。

- フォームのスレッド（ボットの返信に「Issue を作成しました: <URL>」がある）は、起票済み（`created`）の投稿として `submissions` に入れます
- 既存 Issue の管理用の投稿（ボットの親の投稿に「この Issue をスレッドで管理します: …」がある）は、取り込み済みとして `adopted` に入れます。管理用の投稿を立て直したりラベルを付け直したりはしません
- 見るのはボットの投稿（消したボットのものも含む）と、設定にあるリポジトリの Issue だけです。Issue の側に `from-slack`（フォームのスレッド）か `slack-thread`（管理用の投稿）が付いていなければ飛ばします。すでに結び付いている Issue と pull request も飛ばします。同じ Issue のスレッドが 2 つあれば古い方を使います
- Slack と GitHub へは読むだけで、投稿もラベルの変更もしません。ステータスの前回の値は入れないので、次の poll が今の状態を記録します。過去の変化は通知せず、それより後の変化から通知します

手順:

1. ボットを作り直したなら、先に新しいトークンを `set-token` で登録し、新しいボットを起票のチャンネルに招待します（履歴を読むのに要ります）
2. `~/.slack-issue-intake-<名前>/bin/slack-issue-intake relink` で候補を確かめます（何も書きません）。`結び付けます:` の行が入れるもの、`飛ばします:` の行が理由付きで入れないものです
3. よければ `~/.slack-issue-intake-<名前>/bin/slack-issue-intake relink --apply` で書き込みます。poll と同じリースを取ってから書くので、poll の最中なら `処理中です` で止まります。少し待って実行し直してください。何度実行しても同じ行を重ねません

遡る履歴は新しい方から 20,000 件まで（200 件 × 100 ページ）です。Slack の呼び出しの上限に当たったら、Retry-After の秒数だけ待ってから続けます。

## Slack CLI を使わないセットアップ

Slack CLI が使えないとき、または `make setup <名前>` の途中でフォームやマニフェストが受け付けられなかったときの手順です。skill `/slack-issue-intake` から進めるか、`node bin/slack-issue-intake.ts --name <名前> guide` で次の案内を表示します。

Slack CLI にログインしているなら、この手順の代わりに `make setup <名前>` を使えます。
1. https://api.slack.com/apps の Create New App → From a manifest で社内向けカスタムアプリを作り、ワークスペースにインストールします。配布しません。有料プランが必要です。

マニフェスト:
```json
{

    "name": "Issue Intake"
  },
  "features": {
    "bot_user": {
      "display_name": "Issue Intake",
      "always_online": false
    }
  },
  "oauth_config": {

      "bot": [
        "channels:history",
        "groups:history",
        "chat:write",

        "users:read",
        "usergroups:read"

    }
  },

    "org_deploy_enabled": false,
    "socket_mode_enabled": false,
    "token_rotation_enabled": false
  }
}
```
2. アプリの設定の OAuth & Permissions を開き、Bot User OAuth Token（xoxb- で始まる文字列）をコピーします。続けて `node bin/slack-issue-intake.ts --name <名前> set-token` を実行します（skill で進めているときは Claude が実行します）。
「slack-issue-intake」という題の入力ウィンドウが開くので、⌘V で貼り付けて OK を押します。入力欄はパスワード用と同じで、貼った文字は見えません。「saved token=」で始まる行が出れば登録できています。
トークンは Claude との会話やコマンドの引数に書かないでください。会話に貼るとモデルに送られて記録にも残り、引数に書くとシェルの履歴に残ります。ウィンドウが開かず fallback=clipboard と出たときは、トークンをコピーした状態で `node bin/slack-issue-intake.ts --name <名前> set-token --from-clipboard` を実行します。
3. 対象チャンネルで /invite @Issue Intake を実行します。

7. `node bin/slack-issue-intake.ts --name <名前> permissions --show` で内容を確認し、承認してから `node bin/slack-issue-intake.ts --name <名前> permissions --apply` を実行します。
8. `node bin/slack-issue-intake.ts --name <名前> enable` を実行します。受け継ぐ許可があれば内容を確認し、承認したときだけ `--accept-inherited` を付けます。
Orca の Claude 起動引数へ --permission-mode や --allowedTools など許可を広げるものを入れないでください。
最初の実行で bypass モードになっていないことを確認してください。bypass なら automation を無効にし、既定引数の --dangerously-skip-permissions を外してください。

### Workflow Builder で手で作る

上の手順 4 の詳しい版です。Slack の画面の文言は言語設定などで変わるため、英語の表示名を括弧に添えています。

1. ワークスペース名 → ツール → Workflow Builder を開き、新しいワークフローを作ります（バグ・要望・新機能・質問の 4 つ。以下をそれぞれ行います）。開始のきっかけには、Slack のリンクから始める（From a link in Slack）を選びます。
2. フォームで情報を集めるステップ（Collect info in a form）を足し、質問を作ります。ワークフローはカテゴリごとに 4 つ作り、質問は上の手順 4 のとおりにします。カテゴリはワークフローで決まるので、フォームでは聞きません。質問の名前は一字一句このとおりにします。文字が違うと投稿を読み取れず、ボットが理由をスレッドに返します。添付ファイルは複数可にします。1個しか受けられない場合は、任意のアップロードの質問を3つ並べます。
3. チャンネルにメッセージを送るステップ（Send a message to a channel）を足し、送り先に対象チャンネルを選びます。メッセージには、上の手順 4 のそのカテゴリのテンプレートをそのまま使い、`{…}` の所にフォームの変数を差し込みます。添付ファイルの変数もメッセージに付けます。
4. 4 つとも公開（Publish）したら、チャンネルの「ワークフロー」タブ →「ワークフローを目立たせる」で 4 つすべてを選び、「注目」を押します。メンバーには入力欄の所にボタンが並びます。
5. 1件送り、`node bin/slack-issue-intake.ts --name <名前> inspect --raw` で `marker=yes`、`parse=ok`、`reporter=U…`、添付の数と同じ `files=` を確かめます。

## 動作確認

1. Orca の既定の Claude 起動引数に --permission-mode や --allowedTools など許可を広げるものがないことを確認します。
2. enable 前は automation が無効、precheck が `<launcher> poll` であることを確かめます。
3. `node bin/slack-issue-intake.ts --name <名前> enable` のあとに `orca automations run <id>` で最初の回を動かし、permission mode が bypass ではなく、手順外の操作が拒否されることを確認します。bypass なら `orca automations edit <id> --disabled` で止め、既定引数から --dangerously-skip-permissions を外してから試し直します。
4. `make setup <名前>` でフォームを作った場合は、チャンネルの入力欄の所に出るボタンからフォームのダイアログが開けることを確かめます。添付付きで送った投稿を `node bin/slack-issue-intake.ts --name <名前> inspect --raw` で見て、marker=yes、parse=ok、起票者の ID、添付の数だけの files があることを確認します。投稿者はこのアプリのボット（bot=yes）です。添付なしでも送れることも確かめます。
5. フォームから添付2個以上を投稿し、`node bin/slack-issue-intake.ts --name <名前> inspect --raw` で marker=yes、parse=ok、起票者と添付数を確認します。API 上の text / blocks、files / file permalink の形は実環境で未確認です。Workflow Builder で作った場合、1質問で1ファイルだけなら任意アップロードを3質問にします。
6. 明確なバグ報告で、ラベル・添付リンク付きの Issue とスレッドの URL を確認します。曖昧な投稿には質問が届き、人が返信したら次の回で拾うことを確認します。Bot トークンの conversations.replies が対象チャンネルで読めるかもここで確認します。
7. 不正なカテゴリは理由を返信し、何も投稿しない15分間は skipped_precheck だけで Claude が起動しないことを確かめます。
8. user の allow を追加すると permissions=changed で止まることを確認し、一覧を承認して `node bin/slack-issue-intake.ts --name <名前> enable --accept-inherited` で戻します。
9. 「質問する」から仕様の質問を送り、次の回でスレッドに回答と根拠のリンクが付くこと、返信すると次の回でまた答えることを確かめます。「バグか仕様なのかわからない」で起票の案内が出たら「起票してください」と返信し、バグ・`priority: middle` の Issue ができることを確かめます。
10. 起票した Issue に Backlog が付くことを確かめます。ラベルを Ready に変えると、次の回でスレッドに「ステータスが Backlog から Ready に変わりました」と書き込まれることを確認します。メンション先を設定した場合は、orca-team-dispatch-task が Ready_Eng にしたときにグループへ通知が届くことを確かめます。

## 運用

`init` は、安定パス `~/.slack-issue-intake-<名前>/bin/slack-issue-intake` を作ります。運用ではこちらを使います。`node bin/slack-issue-intake.ts --name <名前> …` と同じ働きで、プラグインを更新してもパスは変わりません。以下のコマンドは、どちらの形でも実行できます。

- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake status`: 件数、返信待ち、失敗、リース、読み取り位置、直近の poll、権限の状態。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake retry --id N`: 失敗を直前の状態へ戻す。メタデータの一時取得失敗も連続10回で failed になり、状態とエラーを確認できます。作成開始時刻・アカウント・作成中の印は残ります。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake inspect [--limit N] [--raw]`: 状態を変えず最新の投稿の解析結果を確認。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake form`（`make slack-form <名前>`）: フォームのボタンを作り、チャンネルのおすすめワークフローにする（入力欄の所にボタンが出る）。`make setup <名前>` の9段目が実行します。始めに仕様の索引も作り直します（`--skip-knowledge` で作らない）。`~/.slack-issue-intake-<名前>/bin/slack-issue-intake form --manifest`（`make manifest <名前>`）はフォーム付きのマニフェストを表示します。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake knowledge [--repo <owner/name>]`（`make knowledge <名前>`）: 「質問する」に答えるための仕様の索引だけを作り直す。ドキュメントを更新したあとに実行します。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake mention --group <ハンドル|表示名|ID>`: ステータスの通知でメンションするグループを変える。`--none` でメンションしない。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake report --source <path|none> --channel <ID|name|default> --daily-at HH:MM`: 定期報告を設定・変更します。材料の既定の場所は `~/.claude/config/orca-team-dispatch-task/auto/<名前>/report.json`。`none` で無効、`default` で起票のチャンネルへ送ります。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake relink [--apply]`: 前のホームや作り直す前のボットが作ったスレッドを、チャンネルの履歴から探して結び付け直す。`--apply` が無ければ候補を示すだけです（「別のマシン・作り直したボットからの引き継ぎ（relink）」）。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake set-token`: トークンを登録し直す。開いたウィンドウに貼り付けます（文字は伏せ字）。`--from-clipboard` はクリップボードから、`--from-stdin` は人がつないだパイプから読みます。
- `~/.slack-issue-intake-<名前>/bin/slack-issue-intake permissions --show` → 承認して `~/.slack-issue-intake-<名前>/bin/slack-issue-intake permissions --apply` → `~/.slack-issue-intake-<名前>/bin/slack-issue-intake enable`。継承した allow / additionalDirectories があると明示承認が必要です。
- 停止: `orca automations edit <id> --disabled`。
- Orca は起動のたびに Claude のタブを新しく開いて残します。終わった回のタブは、次の poll が 3 分静かになってから閉じます（動作中の回と、人が開いた端末は閉じません）。回の結果は `orca automations runs --id <id>` で読めます。

権限が変わると changed または unsafe で止まり、設定を直して enable をやり直します。`creating … inflight=` がある間は送り手の終了と待機時間を待ちます。印を消して作り直してはいけません。
`poll` は仕事あり0、仕事なし・処理中・権限不備1、未設定2、Slack の致命エラー3です。45秒の予算を各外部呼び出しへ渡します。取り込みのあと10秒以上残っていれば、ステータスの通知を行います（出力の `notified=`）。通知の失敗は `partial=true` と errors に出ますが、終了コードは変えません。手動 Run now は precheck を通りません。collect は自分で同期します。

既存 Issue は、更新順の増分走査と、作成順に1回1ページずつ見直す走査の2本で探します。増分の走査が他者の更新で読み落としても、見直しが一周のうちに拾います。1回に立てるスレッドは5件までで、うち1件分は見直し用に残します。走査を始めるリポジトリは poll ごとに1つずつずらします。見直しの一周に必要な poll は、リポジトリごとに多くても「（開いている Issue の数 ÷ 100（切り上げ）＋ その周で見直しが拾った数）× thread のリポジトリの数」です。時間が足りない回はその分遅れます。

予定をDBへ残してから投稿・ラベル付与へ進むため、閉じられた Issue も途中から再開します。投稿直後に停止すると同じ「管理します」の投稿が1回重なることがあります。読めない Issue（削除、権限不足など）の行は削除せず、毎回 errors に出して再試行します。投稿とラベル付与はそれぞれ1回5件まで、試した行を待ちの末尾へ回すので、失敗が続いてもほかの行へ順番が回ります。poll の結果には `adopted=` と `report=new|updated|unchanged|off|failed`、`learn=<投稿数>/<依頼数>` が付きます。定期報告は取り込みより先に実行します。

## 制約

- 添付バイナリは GitHub に上げません。Issue には Slack の file permalink を載せます。Slack にログインした人だけが開けます。画像5MB、テキスト・JSON 1MBまでを判断用にダウンロードします。各メッセージ10ファイルまで、Issue のリンク一覧は50件までです。本文全体の60,000文字に収まらないときは、リンクを途中で切らず末尾から省き、省略件数を表示します。
- Mac 1台で、Orca が開き Mac が起きている間だけ動きます。停止中の履歴は起床後にページ単位で追いつきます。init より前は拾いません。
- precheck の結果は Orca の実行履歴に skipped_precheck として溜まります。5分間隔なら1日288行です。
- クラッシュの間合いによって Slack の返信がまれに重複します。
- チャンネル、ワークスペース、gh のログイン名は固定します。リポジトリは複数登録でき、追加と既定の変更ができます。チャンネルなどを変更する場合は automation を止め、ホームを退避して設定し直します。
- Issue 作成後の返信は、ボットにメンションしたものだけを Issue へ転記します（「Slack の返信を Issue に転記する」）。Webhook と常駐プロセスは対象外です。Issue の変化はステータスと開閉だけを知らせ、コメントは AI のマーカー付きのものだけを転載します。
- ステータスの通知は、Slack に書いた直後に処理が落ちると、同じ通知が 1 回重なることがあります。

## 重複防止の保証の範囲

1. すべての送り手が同じ Mac で動くこと。
2. 要求を送りうる親と gh の子がすべて止まってから90秒以内に、GitHub がすでに受け取った要求を処理し終えること。
3. 運用中に gh のアカウントを変えないこと（変わったら作成を止めます）。

送り手の PID と起動時刻を保存し、生きている間は作り直しません。すべて止まったと初めて確認した時刻から90秒待ち、一覧の全ページを作者と最後の行のマーカーで照合します。子は身元を DB に記録してから go を送るゲートを通ります。応答を失っても、次の処理は一覧で採用します。

## セキュリティ

Claude は run ごとの work.json と添付、仕様の索引（ホームの knowledge/ の下）を読み、decisions.json だけに判断を書きます。送り先・タイトル・ラベルと副作用は CLI が管理します。投稿・返信・添付内の指示には従いません。
project は dontAsk と disableBypassPermissionsMode、実行コマンドとファイルの限定 allow、外部操作の deny を持ちます。user には secrets.json の Read / Edit の deny を足します。token は0600、ホームは0700で保存し、外部文字列は保存・出力前に伏せます。
enable は必要な設定、local 設定の不在、managed モード、秘密ファイルの deny を検査します。project 全体と user / managed の permissions 全体の指紋を保存し、poll は毎回検査と指紋の一致を確認します。allow だけでなく deny やモードの変化でも止まります。ただし、同じ親ディレクトリにある別の有効な intake ホームの secrets.json に対する user の Read / Edit の deny は指紋から除きます。別ワークスペースの設定を足しても既存ホームの承認を保つためで、自分の秘密ファイルの deny の欠落は今までどおり停止します。
hook と mod による承認は検査・指紋の対象外です。Orca が加える既定引数も読み取れないため、許可を広げる引数がないことが前提です。--dangerously-skip-permissions を拒む設定が実際に dontAsk を保つかは初回の動作確認で確かめます。
