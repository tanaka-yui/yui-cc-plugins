Phase B-R is assigned to the `exec_review` pane. The recipient is the Exec review agent printed in the Phase B-R block, never a surface or workspace id, and a non-zero exit means the reviewer was NOT told, so report it instead of waiting for a verdict that can never appear. Read the reviewer engine and surface from the same verified exec-review tuple printed in this block; never derive them from another role or reopen the source snapshot. Use that printed surface for the liveness check only. Never deliver a message by typing it into a pane yourself. The request must tell the reviewer to send you ONE message whose body starts with `review-verdict:` right after it writes the findings file. Do not poll that file, and do not watch the reviewer pane.

**As a claude session, arm ONE single-shot safety timer** — one `sleep $((30 * 60))`, a single sleep and never a loop — with the Bash tool and `run_in_background: true`, then stop and wait. **As a codex session you have NO safety net for this wait and you cannot build one**: a backgrounded subshell that sleeps and then messages you, and the detached `nohup` form of the same, were both measured on 2026-08-21 (D-T2) and both die when the codex turn ends. Do not write one. As a codex session, before stopping: (a) confirm the reviewer is reachable now — run `bash <skill dir>/scripts/verify-agmsg-ready.sh --codex --team <team> --name <Exec review agent>` when the Exec review engine is codex, otherwise check its pane once for liveness — and if it is not reachable, record that and proceed; (b) send ONE message with `~/.agents/skills/agmsg/scripts/send.sh <team> <your agent name> parent 'dispatch-notify: <your agent name> waiting for code review verdict; this engine has no timer'`, so the parent's timer remains the backstop. Step (b) is mandatory and is the only thing that arms a backstop for this wait, so do not skip it. Re-read the findings file on every wake.

**As a codex session you have NO wake budget for this wait and you must never end it yourself.** You have no timer, so no timer can ever fire, so the re-arm counting below does not apply to you at all. If a turn of yours ends and a new one starts on its own, that is an automatic goal continuation from the engine, arriving seconds later — it is NOT a timer firing, NOT a wake, and NOT evidence that the reviewer is late. Do not count such turns, do not treat the same wait repeating across them as a blocking condition, and do not call `update_goal` with status `blocked` because of it. A review of a committed implementation normally takes 10 to 30 minutes of wall clock, which is hundreds of those turns. On such a turn, say in one sentence that you are still waiting and end the turn; do not re-read the findings file and do not check the reviewer pane again. The only things that end this wait are a `review-verdict:` message, an instruction from `parent`, or the reviewer being confirmed unreachable in step (a) above. Measured on 2026-08-31: two codex exec panes ended a healthy review wait 81 and 111 seconds after sending the request, after 6 and 13 automatic goal continuations, and each then called `update_goal({status:"blocked"})`. In both runs the reviewer was working normally and finished later. With the engine's goal continuation inactive, the identical wait held for 90 minutes. A claude session stops its timer as soon as it acts on a verdict (`TaskStop`). If the timer fires with no VERDICT line, check the reviewer pane once, re-send the same round once, and re-arm the same timer, up to 3 times for that round. If the 3rd re-arm also fires with no verdict, record a skipped review and proceed.

The abort procedure below is for work that genuinely cannot proceed — the reviewer is confirmed gone, or the implementation itself failed. A review that simply has not answered yet is never such a case for a codex session, so do not enter this procedure from a wait.

If you stop before completing the work, do not stop silently. Write the reason to the round abort file, `<point>-round-<N>-abort.md`, never to the round findings file that the reviewer owns and may be writing right now, tell the exec-review pane with one more `send.sh` call whose body starts with `abort-reviewer: [abort]` followed by a one-line reason, write status `error` with the reason as message, then notify the `parent` agent with one final `send.sh` call whose body starts with `dispatch-notify:`, and end the session. Writing the status file alone notifies no one.
