# --auto の make setup（C3b）: 遠くのマシンでの確認と、AI による確認コマンドの割り出し

対象: `apps/orca-team-dispatch-task`。元の設計は `2026-11-12-issue-auto-dispatch-design.md` の 6.8 と、`2026-11-13-auto-dispatch-additions-design.md` の 6.2。前半は `2026-11-17-auto-setup-design.md`（C3a）。

## 目的

`make setup` を済ませれば、**遠くのマシン（Mac M2max など）にも Issue が振り分けられ、PR まで届く**ようにする（2026-11-17 のユーザーの言葉: 「PR まで届くという意味です」）。「とりあえず動く」ところまでが今回の範囲。

今の状態: C3a の setup は遠くのマシンの組を `verified: false` のまま保存する。tick は、対象のリポジトリで確認済みの組があればそこにだけ振り分ける。1 つも無ければ確認済みでない組にも振り分けるが、その Issue には「確認が通っていないマシンで実装」が付き、merge の前に In review に回る（`lib/auto-tick.ts` の振り分け）。つまり、このマシンが確認済みなら遠くのマシンは使われず、使われても自動では仕上がらない。振り分けから PR までの流れ自体は、C2b の実機（2026-11-16 / 17）で M2max でも通っている。足りないのは、setup が遠くの組を確認済みにする手段だけ。

## やること

1. **遠くのマシンで確認コマンドを走らせ、通れば確認済みにする**（中心）。
2. **確認コマンドを走らせる間の最大メモリとディスクの増え方を測り**、並列数の推奨値に使う（このマシンと遠くの両方）。
3. **AI（`claude -p`）に checkout を読ませて、確認コマンドと必要な道具の案を出させる**。人が直して決める。
4. 道具が足りないときは、何が足りないかを人に見せる（入れはしない）。

## やらないこと

- 足りない道具を入れること、sudo を AI に許すかの質問、swap を作ること（元の設計 6.8 の 3 と 5）。次の段階に回す。worker への依頼は今のとおり sudo を使わない決め打ちのまま。
- tick・判定・振り分け・後片付けの振る舞いを変えること。tick は今のとおり `verified` を見るだけ。
- Windows の環境での確認（C3a と同じく測定は null、人の判断に任せる）。
- 遠くの checkout を最新にすること（`git fetch` / `pull`）。このマシンの確認（C3a）と同じく、checkout の `HEAD` から切って走らせる。

失敗の形として避けたいこと（anti-goal）:

- 確認のために遠くの checkout を汚す・ブランチを残す（build の生成物が残ると、その checkout からの dispatch が「未コミットの変更」で止まる）。
- 確認が終わったか分からないまま setup が先へ進み、確認済みでない組を確認済みとして保存する。
- AI の案をそのまま確定させる（人が見ずに確認コマンドが決まる）。

## 作り方（ユーザーが選んだもの）

2026-11-17 にユーザーが A を選んだ。

| 案 | 中身 | 判断 |
|---|---|---|
| **A. Orca の端末で遠くに走らせる** | C3a のスペック測定（`probeRemote`）と同じく、遠くの checkout に Orca の端末を作り、node のスクリプトで一時的な git worktree を切って確認コマンドを走らせ、目印つきの JSON を出させて親が読む | **採用**。実機で動いた仕組みの延長で、確認も本物。最大メモリとディスクも同じスクリプトで測れる |
| B. 人が「確認済み」と答えるだけ | 何も走らせない | 確かめないので、道具が足りないと worker が失敗して Failed になるだけ |
| C. 遠くに Orca の worker（Claude）を起こす | 割り出しも確認も worker が行い、mail で返す | 動く部品が多く、「とりあえず動く」までが遠い |

## 設計

### 1. 確認のスクリプト（このマシンと遠くで同じもの）

- C3a の `PROBE_SCRIPT` と同じ形（node の 1 行を base64 で包み、`node -e` で走らせる）の、新しい確認用スクリプトを作る。入力（確認コマンドの列、確かめる道具の名前の列、測るかどうか）はスクリプトに埋め込む。
- スクリプトの中身:
  1. `git worktree prune`。一時ディレクトリを作り、`git worktree add --detach <tmp> HEAD`。
  2. 確認コマンドを順に `/bin/sh -c` で走らせる。環境に `GIT_PAGER=cat`、`PAGER=cat` を足す（C3a の実機で見つけた止まり方を避ける）。
  3. 各コマンドの最大メモリを測る。macOS は `/usr/bin/time -l`（最大の resident set size はバイト）、Linux は `/usr/bin/time -v`（kbytes）。`/usr/bin/time` が無いとき・読めないときは null。
  4. ディスクの増え方は、走らせる前と後の一時ディレクトリの大きさの差（`du -sk`）。
  5. 最初に失敗したコマンドで止める。
  6. 確かめる道具（下の 3）を `command -v` で引き、無いものを集める。
  7. 一時 worktree を `git worktree remove --force` で消し、`git worktree prune`。
  8. 結果を `@@orca-auto-verify:begin@@{...}@@orca-auto-verify:end@@` の 1 行で出す。中身は `{ ok, failed, exitCode, peakMemoryMb, diskGrowthMb, missingTools, platform }`。
- 確認コマンドの出力は端末にそのまま流す（人が Orca の画面で進みを見られる）。親は目印の行だけを読む。
- このマシンでは、C3a の `runVerifyLocal` をこのスクリプトを `node -e` で走らせる形に置き換える（出力は今のとおり端末へ）。このマシンと遠くで測り方を揃えるため（私の判断）。

### 2. 遠くでの走らせ方

- `probeRemote` と同じく `orca terminal create --environment <id> --worktree <その組のセレクタ> --command <スクリプト>` で端末を作り、`terminal read --environment <id>` で目印の行を待つ。終わったら必ず `terminal close`。
- 確認コマンドは build やテストで長くかかるので、読み取りの間隔と上限を測定より長くとる。上限の既定は 30 分（定数。テストでは環境変数で縮める。値は builder が決めてよい）。待っている間は、何分たったかを数分おきに表示する。
- 上限を超えたら、端末を閉じ、その組を確認済みにせず「時間内に終わらなかった」と表示する。遠くに一時 worktree が残りうるので、次の確認の最初の `git worktree prune` と、残った一時ディレクトリの場所の表示で人が消せるようにする。
- 端末の出力は長い行が折り返される（C3a の未確認 1）。目印の begin と end の間を、改行を詰めてつなげて読む（`probeRemote` と同じ作り）。

### 3. AI による確認コマンドの割り出し

- 確認の段（段 7）で、リポジトリごとに、確認コマンドを聞く前に「AI に確認コマンドを割り出させますか」を聞く。既定は、そのリポジトリに確認コマンドがまだ無ければ yes、あれば no。
- このマシンの checkout で `claude -p` を 1 回走らせる。
  - 読み取りの道具だけを許す（`Read`・`Glob`・`Grep`）。書き込み・Bash は許さない。
  - モデルと effort は、その設定の `judge.model` / `judge.effort`（判定と同じもの。私の判断）。
  - 読ませるもの: CI の定義、`package.json`、`Makefile`、`go.mod`、`pyproject.toml`、`mise.toml` / `.tool-versions`、compose のファイル、README など（元の設計 6.8 の 1）。言語やフレームワークを決め打ちしない。
  - 出させるもの: JSON `{ commands: string[], tools: string[], notes: string }`。`commands` は「build・test・lint を、副作用なく、人の入力なしで走らせる」コマンドの列。`tools` はそれに要る道具のコマンド名。
- 案を表示し、`commands` を確認コマンドの質問の既定値にする。人は Enter で受けるか、書き直す。
- 失敗（claude が無い、時間切れ、JSON が読めない）は表示して、今までどおり手で入力する流れに戻る。setup は止めない。
- `tools` は、確認のスクリプトで各マシンに `command -v` で引く（上の 1 の 6）。設定には保存しない（私の判断。次の段階で道具を入れるときに持ち方を決める）。確認のときだけ、AI の案がある回は案の `tools` を使う。

### 4. 確認の段（段 7）の流れ

リポジトリごとに:

1. （任意）AI の割り出し → 案の表示。
2. 確認コマンド・インフラか・CI があるかを聞く（C3a のまま）。
3. このマシンがそのリポジトリを扱うなら、このマシンで走らせるかを聞く（C3a のまま。走らせ方だけ 1 のスクリプトに変わる）。
4. **遠くのマシンのうち、そのリポジトリの組を持つものごとに、「<マシン名> で走らせて確かめますか」を聞く**。既定は、その組が変わっていない（C3a の「変わっていない組」の規則）なら no、変わったか未確認なら yes。
5. 結果を表示する: 通った／失敗したコマンド、最大メモリ、ディスクの増え方、足りない道具。足りない道具があれば、何が足りないかと、どのマシンかを並べる（入れ方は書かない）。
6. 通った組だけ `verified: true`。失敗・時間切れ・つながらないは `false`。

確認済みを保つ規則（C3a で決めたもの）は変えない。全体の `repos[r].verified` は、今のとおりこのマシンの結果で決め、遠くの結果では決めない。

### 5. 測った値の持ち方と並列数

- マシンの組に、測った値を足す: `hosts[].repos[r].measure = { peakMemoryMb, diskGrowthMb, measuredAt } | null`。読み込みの検査は C3a の `spec` と同じ考え方（無い・null は null、形が違えば設定ごと不正）。
- 引き継ぎは `verified` と同じ「変わっていない組」の規則に揃える（私の判断）: 走らせ直さなかった組は、変わっていなければ前の `measure` を残し、変わっていれば null。走らせた組は、その回の結果（`/usr/bin/time` が読めなければ null）で置き換える。Enter だけのやり直しで `measure` が消えて推奨値が定数に戻らないようにするため。
- 並列数の推奨（段 8）で、そのマシンの組の `measure` があれば、1 worktree 分のメモリとディスクを、組の中の最大値に置き換える。無ければ今の定数（`SETUP_WORKTREE_MEMORY_MB`、`SETUP_WORKTREE_DISK_MB`）。測った値には余裕の倍率を掛ける（値は builder が決める。build 以外の worker 自身の分を見込むため）。
- 表示に、どちらの値を使ったか（測った値か、定数か）を出す。
- C3a で決めた「hosts の無い形」（`hosts` を書かない設定）には `measure` を持たせない。全体の並列数は今のまま人が決める。

### 6. 保存と再開

- 下書き（`setup.json`）に、組ごとの `verified` と `measure` が入る。段 7 は 1 つの段のままで、下書きは段の終わりにだけ書く（C3a のまま）。途中で止めたら段 7 の最初からやり直し、その回に通った組の結果は捨てる（私の判断。「とりあえず動く」を優先し、C3a の確認済みを保つ規則に手を入れない。確認に時間のかかるリポジトリでは走らせ直しになるのが代償）。
- Enter で飛ばせる（既定が no になる）のは、前の回で保存の段まで進んで `config.json` に確認済みとして書かれた組だけ。
- `configJsonFromDraft` は `measure` を書く。

## 実機での確かめ（親が行う）

1. このマシンと Mac M2max、orca-auto-e2e / -2 で `make setup` をやり直し、M2max の両方の組を確認済みにする。測った値が出て、並列数の推奨に使われる。M2max の checkout に一時 worktree とブランチが残らない。
2. AI の割り出しで、案が出て、Enter で確認コマンドになる。
3. M2max だけに振り分けられるようにして（このマシンの並列数を 0 にはできないので、このマシンでそのリポジトリを扱わない組にするなど、方法は親が決める）、Ready＋`from-slack` の Issue が M2max で実装され PR まで届く。このとき M2max の組が `verified: true` で、Issue の理由に「確認が通っていないマシンで実装」が付かないことも見る（確認済みの組が無いと tick は確認済みでない組にも振り分けるので、PR が届くだけでは C3b が効いた証にならない）。
4. 失敗するコマンド（例 `false`）で、M2max の組が確認済みにならず、理由が出る。

## 未確認（実機で見る）

- 長い確認コマンド（数分以上）の間、`terminal read` が出力を返し続けるか。目印の行が出力の量に押し流されないか（`terminal read` の既定は最後の 120 行。目印は最後に出るので読めるはず）。
- 遠くの `/usr/bin/time` の出力の形（macOS と Linux）。
- `claude -p` を setup の中から起こしたときの許可の出方（読み取りの道具だけで止まらないか）。

## 決めたこと（私の判断）

- このマシンの確認も同じスクリプトに揃える。
- AI の割り出しは判定と同じモデルを使い、読み取りだけを許す。案の `tools` は設定に保存しない。
- 時間切れの上限の既定は 30 分。
- 段 7 は 1 つの段のまま。途中で止めたら段 7 の最初から、その回に通った組の結果は捨てる。
- 走らせ直さなかった組の `measure` は、`verified` と同じ「変わっていない組」の規則で引き継ぐ。

## 作る人に任せること

- スクリプトの細部（`/usr/bin/time` の出力の読み方、`du` の扱い）、読み取りの間隔、余裕の倍率の値、`claude -p` のプロンプトの文面と JSON の取り出し方、テストの組み方。
