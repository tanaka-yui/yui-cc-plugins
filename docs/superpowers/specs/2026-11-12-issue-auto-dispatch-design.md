# Slack フォームの分割と Issue の自動消化 設計

日付: 2026-11-12
対象: `apps/slack-issue-intake`、`apps/orca-team-dispatch-task`

## 1. 目的

Slack のフォームから起票された Issue を、人が「やる」と決めたものから AI が順に実装し、結果を元の Slack スレッドへ返す。人は Slack と GitHub のラベルだけを見て判断できるようにする。

今の問題は次のとおり。

- フォームの本文が 1 つの自由記述で、カテゴリごとに必要な情報（バグなら事象とエラーログ、要望なら現在と理想）が集まらない。投稿も見出しや区切りがなく読みにくい。
- `orca-team-dispatch-task` の issue モードは、難易度を見ずに着手し、優先度の順番がなく、ステータスの管理もない。まとめて流して全部終わるまで待つ方式（最長 24 時間）のため、定期起動のキューとしては使えない。
- 実装の進み具合が Slack に戻らない。

## 2. 範囲と順番

3 つの部分に分け、この順に作る。B は A の投稿形式を使い、C は B のラベルとコメントの約束を使う。

| 部分 | プラグイン | 内容 |
|---|---|---|
| A | slack-issue-intake | フォームをカテゴリごとの 3 つのボタンに分け、投稿の見た目を整える |
| B | slack-issue-intake | 起票時に Backlog を付け、ステータスの変化を元のスレッドへ通知する。setup でメンション先のグループを入力する |
| C | orca-team-dispatch-task | ステータスラベルの共通化、`--auto` モード（難易度判定、優先度つきキュー、複数リポジトリ、後片付け）、環境の確認と並列数の判定、`make setup` |

## 3. 目標・非目標・してはいけないこと

### 目標

- 起票者がカテゴリに合った項目を迷わず埋められる。
- 人がラベルを Ready にしたものだけを AI が拾い、優先度の高い順に処理する。
- 結果が明らかな小さな修正は、人の手を介さずに PR → merge → Done → close まで進む。
- AI が自分で判断した点がある変更、重い変更は、必ず人に回り、`@グループ` に知らせる。
- 1 つの Issue がフロントエンドとバックエンドのように複数のリポジトリにまたがっても扱える。
- 言語やフレームワークを決め打ちしない（Go / TypeScript / Python / bash / Node、コンテナで動く API や React の画面、Terraform など）。
- 小さな EC2（t3.xlarge 程度）でもメモリ不足で落ちない。

### 非目標

- フォームの中で、選んだカテゴリに応じて入力欄を切り替えること。Slack 組み込みの `open_form` は静的なフォームで、入力に応じて変えられない（公式ドキュメント）。常駐サーバーを持つ方式は、この仕組み全体の前提（常駐しない）と合わないので採らない。
- `--issue` モードの回し方（まとめて流して待つ方式）を変えること。`--issue` で変えるのはラベルと並列数の推奨だけ。
- orca-team-dispatch-task から Slack へ直接投稿すること。Slack への通知は slack-issue-intake が受け持つ。
- 複数の GitHub リポジトリの Issue を拾うこと。拾う Issue は 1 つのリポジトリ（slack-issue-intake の起票先）だけ。

### してはいけないこと（技術的に動いても失敗とみなす）

- 確認できていない変更（build / test / lint を通せなかったもの、CI が落ちたもの）を AI が merge する。
- Terraform などのインフラのリポジトリで、AI が `plan` / `apply` を実行する、またはその PR を自動で merge する。
- 人が付けた Backlog / Pending / Ready_Eng / In review のラベルを AI が書き換える（後述の決まった遷移を除く）。
- 秘密の値（Slack トークン、`.env`、クラウドの認証情報）をログ、コメント、PR、Slack に出す。
- worktree やローカルのブランチが溜まり続けて、ディスクを使い切る。

## 4. 部分 A: フォームを 3 つのボタンに分ける

### 4.1 入口

チャンネルの入力欄の所に、3 つのボタン（おすすめワークフロー）を並べる。どのボタンを押したかでカテゴリが決まり、フォームにカテゴリを選ぶ欄は置かない。

マニフェストのワークフローは 3 つにする（`issue_intake_bug` / `issue_intake_request` / `issue_intake_feature`）。それぞれ組み込みの `open_form` と `send_message` だけで作る。今の `issue_intake_form` はマニフェストから消し、古いトリガーは `form` の再実行で削除する。

フォームの題は `open_form` の制約（半角 24、日本語 8 字まで）に収める。ボタンの名前と題の文言は builder が決める。

### 4.2 フォームの項目

| ボタン | カテゴリ別の項目 | 共通の項目 |
|---|---|---|
| バグ | 事象（必須・複数行）、エラーログ（任意・複数行）、対応策（任意・複数行）、画面のURL（任意・1 行）、ソースコードのパス（任意・1 行） | タイトル（必須）、優先度（必須、critical / high / middle / low）、添付ファイル（任意） |
| 要望 | 現在（必須・複数行）、理想（必須・複数行）、画面のURL（任意・1 行）、ソースコードのパス（任意・1 行） | 同上 |
| 新機能 | 仕様（必須・複数行） | 同上 |

項目の名前はユーザーが決めたもの。表示の順番は「タイトル、優先度、カテゴリ別の項目、添付ファイル」とする（私の判断）。

### 4.3 投稿の形

ユーザーの承認済み。

- 項目名は太字にする。
- 複数行の項目の値は ``` で囲む。1 行の項目は囲まない。
- タイトル、カテゴリ、優先度、起票者は空行を入れずに並べる。事象から下は、項目ごとに 1 行の空行で区切る。本物の区切り線は `send_message` では使えないので使わない。
- 任意の項目が空でも、`send_message` では省けない。空の枠がそのまま出る（ユーザーに説明済み）。

~~~text
[issue-intake]
*タイトル:* ログイン後に白い画面になる
*カテゴリ:* バグ
*優先度:* high
*起票者:* <@U123>

*事象:*
```
ログインボタンを押すと真っ白になる
```

*エラーログ:*
```
TypeError: ...
```

*対応策:*
```
```

*画面のURL:* https://example.com/dashboard

*ソースコードのパス:* src/pages/dashboard.tsx
~~~

`send_message` の `message` で `*…*` が太字になるか、``` がコードブロックになるかは、実環境で確かめる（README の「実環境では未確認」の一覧に足す）。

### 4.4 読み取り（parse）

`lib/parse.ts` を新しい形に合わせる。

- 項目名の前後の `*` を外してから照合する。
- 複数行の項目は、次の項目名の行までを値とし、前後のフェンス（```）を外す。値に ``` が含まれて枠が崩れた場合でも、次の既知の項目名の行までを値とする。
- カテゴリはメッセージ中の「カテゴリ」の行から読み、カテゴリごとの必須項目を確かめる。
- `SubmissionFields.body` は、項目の並び（項目名と値の組の配列）に置き換える。
- **古い形（`本文:` の 1 項目）も引き続き受け付ける**（私の判断）。切り替えの前に投稿された未処理のものと、手で作った Workflow Builder のワークフローを壊さないため。

### 4.5 Issue の本文

`lib/issue-body.ts` の「元の投稿」の部分は、項目ごとの見出しつきで並べる。要約と詳細（`summary` / `details`）は今どおり Claude が書く。`procedure.md` の `details` の指示は、カテゴリ別の項目名に合わせて直す（procedure-ja.md、lib/permissions.ts、CA9 もそろえる。プラグインの CLAUDE.md の決まり）。

### 4.6 手で作る手順

`renderGuide` / `renderTemplate`（README の「Workflow Builder で手で作る」）も、3 つのワークフローを作る手順と、カテゴリごとのテンプレートに直す。

## 5. 部分 B: ステータスの通知（slack-issue-intake）

### 5.1 ステータスラベル

両方のプラグインで共通にする。名前はユーザーが決めたもの。Failed はユーザーの指示で追加した。

| ラベル | 付ける人 | 意味 |
|---|---|---|
| Backlog | slack-issue-intake（起票時） | 起票直後。人の判断待ち |
| Ready | 人 | やる。AI が拾う対象 |
| Pending | 人 | 後回し。人が見て分かるためのもので、AI はさわらない |
| Ready_Eng | AI（難易度判定） | 重い・長い・新機能など。エンジニアが対応する |
| In progress | AI | AI が実装中 |
| In review | AI | PR を出して人の判断待ち |
| Done | AI または人 | 完了。close する |
| Failed | AI | AI が失敗した |

1 つの Issue には、ステータスラベルを 1 つだけ付ける。色と説明は builder が決める。定義は両方のプラグインの `defaults` に持つ（プラグインは別々にインストールされるため、共有のパッケージを作らない）。2 つの定義が一致していることは、ルートのテストか `pnpm check` で確かめる（私の判断）。

### 5.2 起票時

`issueLabels` に `Backlog` を足す。`ensureLabels` の対象にステータスラベル 8 つを足す。

### 5.3 通知

`poll` の毎回（今の automation の precheck）で、`from-slack` のラベルが付いた Issue のステータスラベルと開閉の状態を読み、前回から変わったものだけを元のスレッドへ書き込む。Claude は起動しない。

- スレッドは、DB の `submissions` の `channel` / `ts` と `issue_number` から引く。
- 前回のステータスは DB に新しい表（例: `issue_status`）を作って持つ。`submissions` の `created` は書き換えない決まりなので、別の表にする。書き込みは poll のリースの下で行う。
- 読む件数を抑えるため、`gh` の検索は更新日時で絞る。具体的な絞り方は builder に任せる。poll の予算（45 秒）と締め切りの決まりを守る。

| 変化 | スレッドへの書き込み | メンション |
|---|---|---|
| → Ready_Eng | エンジニアへの依頼。AI の判定理由を添える | `@グループ` |
| → In review | 人の判断の依頼。AI が自分で決めた点の一覧と PR を添える | `@グループ` |
| → Done（AI が merge した） | AI が自動で Done にしたこと、PR、何を変えたか | `@グループ` |
| → Done（人が PR を merge し、AI がラベルを Done にして close した） | 完了したこと | なし |
| → Done（人が変えた）／ close | 完了したこと | なし |
| → Failed | 失敗したことと理由（「環境不足」「上限時間を超えた」かどうかも） | `@グループ`（私の判断） |
| 進みが止まっている（6.5） | 止まっていること、経過時間、上限時間 | `@グループ` |
| それ以外の変化 | ステータスが変わったこと | なし |

**すでにある Issue**: この機能を入れる前からある `from-slack` の Issue には、Backlog を付けない。最初の poll では今の状態を記録するだけにし、通知は出さない（私の判断。一度に大量の通知が出るのを避けるため）。

### 5.4 2 つのプラグインの約束（Issue のコメント）

orca-team-dispatch-task はラベルを動かすたびに、その理由を Issue のコメントに書く。コメントの最終行に、隠しマーカーを置く。

```text
<!-- orca-auto:<status>:<generation>:<event> -->
```

**書く順番**: コメントを先に書き、そのあとでラベルを動かす。slack-issue-intake は、ラベルと合わない最新のマーカーを「ラベルがまだ付いていない」とみなして次の回へ回す。逆の順番だと、間に poll が挟まったときに AI の通知が人の変化として流れる（実装時のレビューで追加）。

`<event>` は、通知の行を見分けるための種類（例: `judged`、`started`、`ai-merged`、`human-merged`、`needs-review`、`partial-merge`、`failed`、`stalled`）。名前の細部は builder が決める。人が PR を merge したのを見て AI が Done にした場合は `human-merged` とし、メンションしない（5.3）。

slack-issue-intake は、ステータスが変わった Issue について、このマーカーのある最新のコメントを読む。マーカーがあれば「AI が変えた」とみなし、コメントの中身（判定理由、PR、AI が決めた点、変更の要約）をスレッドへの書き込みに使う。マーカーが無ければ「人が変えた」とみなす。コメントの本文の書式は builder が決める。ただし、両方のプラグインのテストで同じ例を使って固定する。

### 5.5 メンション先

`make setup` に段を 1 つ足し、メンションする Slack のユーザーグループを入力してもらう。

- 名前（例: `dev-member`）を入力してもらい、`usergroups.list` で ID を引いて config に保存する。書き込みでは `<!subteam^ID>` を使う。
- そのためボットの権限に `usergroups:read` を足す。マニフェストの指紋が変わるので、次の setup で deploy し直しになる（今の仕組みのとおり）。
- 空のまま進めた場合は、メンションしない。

## 6. 部分 C: 自動消化（orca-team-dispatch-task）

### 6.1 ラベルの共通化

`dispatch/in-progress|done|failed` をやめ、5.1 のステータスラベルに置き換える。

- `--issue` も In progress / Done / Failed を使う。
- `--issue` の検索で除外する条件は、In progress / In review / Done / Failed / Ready_Eng / Pending / Backlog と、**古い `dispatch/*` の 3 つ**にする。古いラベルを除外に残すのは、すでに付いている Issue を誤って拾わないため（私の判断）。
- `--auto` を設定したリポジトリで `--issue` を動かす場合は、Ready も除外する。`--auto` はキューに入れている間も Ready のままにするので、2 つのモードが同じ Issue を取り合わないようにするため（私の判断）。
- `--issue` でラベルを動かす処理（claim、claim の取り消し、終端、close）は、今の場所（`issue-fetch.ts` と `orca-issue.ts` の `labelTerminal`）で名前を置き換える。

### 6.2 `--auto` の回し方

Orca の automation で数分おきに起動し、1 回の起動（以下「1 回」）は短時間で終わる。待ち続けない。これにより、今の issue モードの問題（待っている間にロックの生存確認が止まり、次の起動に乗っ取られる。取り残しが 1 件でもあると以降すべて止まる）を避ける。

1 回の流れ:

1. **同期**: 拾う対象リポジトリの Issue のラベルと、各レーンの worker の状態、PR の状態を読む。
2. **後片付け**: In review の Issue で、関係する PR がすべて merge 済みなのに Done になっていなければ、Done にして close する（ユーザーの指示）。
3. **終わった worker の仕上げ**: 6.6 のとおり。
4. **人による変更への対応**: In progress の Issue のラベルを人が別のものに変えていたら、その worker を止め、ブランチを push してから worktree を消す（私の判断）。
5. **判定**: 新しく Ready になった Issue の難易度を判定する（6.3）。
6. **補充**: 空いているレーンに、キューの先頭から入れる（6.4、6.5）。

Claude が必要なのは 5 の判定だけ。slack-issue-intake と同じく、precheck（TypeScript だけで動く）で 1〜4 と 6 の準備を行い、判定が必要なときだけ Claude を起動する形にする（私の判断）。判定が要らない回は Claude を起動しない。

状態ファイルとロックは、リポジトリの外（例: `~/.claude/config/orca-team-dispatch-task/auto/<名前>/`）に置く。拾う対象のリポジトリと、実装するリポジトリが別でありうるため。1 回は短いので、ロックの寿命は 1 回の長さで決めればよい。

### 6.3 難易度の判定

Ready の Issue 1 件につき 1 回だけ行う。ただし、人が Failed や In review の Issue を Ready に戻した場合は、新しい世代としてもう一度判定する（今の issue モードの「一度扱ったものは二度と拾わない」はやめる）。

**Ready に戻されたものは続きから行う**（ユーザーの指示）。

- 前の世代のブランチ（remote に push 済み）から worktree を作り直し、開いている PR をそのまま使う。
- worker には、前の世代からあとに付いた PR のレビューコメント、PR と Issue のコメント、CI の結果を渡し、それに応えて直させる。
- 前の世代の PR が人の手で閉じられていた場合は、ブランチから新しい PR を作る（私の判断）。
- 6.2 の手順 2 で「merge 済みか」を見る PR は、今の世代が使っている PR とする。

判定の結果:

- **行き先**: 自動で実装する（キューへ）／ Ready_Eng。
- **対象リポジトリ**: setup で登録した関連リポジトリのうち、どれに手を入れるか。
- **上限時間**: 難易度から AI が推奨の上限時間を決める（ユーザーの指示）。設定の最大値（既定は builder が決める）を超える値にはしない。上限時間を長く見積もる必要があるものは、レーンを長く占有するので Ready_Eng の候補になる。
- **理由**: Issue のコメント（5.4 の形）に書く。上限時間も書く。

Ready_Eng にする条件（ユーザーの指示と私の判断）:

- 難易度が高い、または長時間レーンを占有しそうなもの。
- カテゴリが新機能のもの（ユーザーの例示）。
- 対象リポジトリが 3 つ以上のもの（私の判断）。

判定に使う model と effort は設定で変えられるようにする。既定は builder が決める。

### 6.4 キューの順番

- 優先度ラベル（`priority: critical` > `high` > `middle` > `low`）の高い順にする。ラベルが無いものは `middle` と同じに扱う（私の判断）。
- 同じ優先度の中では、Ready になった順（古い順）にする。
- critical が来たら先頭に入れる。実装中の worker を止めて割り込ませはしない（私の判断）。
- キューに入っている間、ラベルは Ready のまま。レーンに入れた時点で In progress にする。

### 6.5 レーンと worker

- レーンの数は、setup で決めた並列数（6.8）。
- レーンに入れる直前に、空きメモリと空きディスクを確かめる。足りなければその回は入れない。
- 1 件が複数のリポジトリにまたがる場合は、対象リポジトリごとに worktree を作り、**1 人の worker がまとめて担当する**。API の形のように両方で合わせる部分がずれないようにするため。使うレーンは 1 つと数える。
- **worker の形は `--auto` 用に新しく作る**（私の判断）。今の `--issue` の worker は、親の端末を Run の coordinator として必須にし（`bin/orca-start.ts` の `ORCA_TERMINAL_HANDLE`）、`merge_ready` を送ったあと親の受理を待ち続ける（二段の完了）。`--auto` には常駐する親がいないので、この形は使えない。`--auto` の worker は次のように動く。
  - 1 件を 1 人の worker が担当する。design_review / exec_review / phase_b のような、別のセッションのレビュー役は起動しない（ユーザーの指示）。
  - **AI どうしのレビューは、worker の同じセッションの中の subagent で行う**（ユーザーの指示）。実装と確認コマンドが通ったあと、PR を出す前にレビューさせ、指摘を直す。
    - 対象リポジトリに `.claude/agents` があれば、そこにあるレビュー向けの agent を使う（cmux-team-dispatch-task が `.claude/agents` から agent を見つける仕組みが先例）。
    - 無ければ、Claude Code の組み込みの汎用 subagent に、レビューの観点を渡して使う（私の判断）。
    - レビューと修正の往復は上限を設ける（回数は builder が決める）。上限までに解消しなかった指摘と、worker が採らなかった指摘は「AI が自分で決めた点」に入れる。つまり In review に回る（私の判断）。
    - レビューの要点（指摘と対応）は PR の本文に書く。
  - 終わったら結果をファイルに書いて終わる。親の受理は待たない。次の回の precheck がそのファイルを読んで仕上げる。
  - worktree の作成、Orca への端末の起動の依頼、`--unattended` 相当の「人に尋ねない」動きは、今の仕組みから使えるものを使う。どこまで共有するかと、複数の worktree を 1 人に渡す方法は builder に任せる。
- worker への依頼には、setup で記録した各リポジトリの確認コマンド（build / test / lint）を含め、実装後に必ず走らせる。
- worker の終わりの報告には、次の 3 つを含める。
  - AI が自分で決めた点の一覧（空なら「結果が明らか」）
  - リポジトリごとの PR と、merge してよい順番
  - 失敗した場合は、環境が原因か（道具が無い、秘密の値が無いなど）

**終わらない worker**（ユーザーの指示と私の判断）

- 上限時間は、難易度の判定で AI が決めた推奨値（6.3）を使う。
- 一定時間（値は builder が決める）進みが無ければ、止めずに `@グループ` に知らせる（5.4 の `stalled`）。同じ worker について知らせるのは 1 回だけにする。
- 上限時間を超えたら worker を止め、Failed にする。理由に「上限時間を超えた」と書く。ブランチは 6.6 の後片付けのとおり push してから消す。人が Ready に戻せば、続きから再開できる（6.3）。

### 6.6 仕上げ（PR、merge、close）

すべての変更は、対象リポジトリの **default ブランチ**への PR にする（ユーザーの指示: main 決め打ちにしない。履歴を残す）。

| 状況 | すること | ラベル |
|---|---|---|
| AI が決めた点が無い。確認コマンドが通った。CI が通った | worker が示した順に PR を merge し、Issue を close | Done |
| AI が決めた点がある | PR を残す | In review |
| CI が落ちた、または確認できないリポジトリを含む、またはインフラのリポジトリを含む | merge しない | In review |
| 実装や確認に失敗した、または上限時間を超えた | — | Failed |
| 複数リポジトリの PR を順に merge する途中で、残りが merge できなかった（衝突、ブランチ保護など） | 残りの PR は残す。どれが merge 済みかを書く | In review（私の判断） |

- CI の結果がまだ出ていないときは、次の回にもう一度見る。
- CI が無いリポジトリでは、worker の確認コマンドが通っていれば merge してよい。
- merge のやり方（merge commit / squash）は、リポジトリで許可されている方法から選ぶ。選び方は builder に任せる。
- PR の本文には、Issue へのリンク（`owner/repo#N`）と、ほかのリポジトリの PR へのリンクを書く。
- Issue の close は、関係する PR がすべて merge されてから行う。
- ラベルを動かすたびに 5.4 のコメントを書く。

**後片付け（ユーザーの指示）**: Done / In review / Failed のどれで終わっても、ブランチを remote に push してから、worktree とローカルのブランチを消す。PR のブランチはすでに remote にある。Failed は、コミットがあればブランチを push してから消す（調べられるようにするため。私の判断）。これは今の「issue モードは資源を消さない」決まりの例外で、`--auto` だけに適用する。`--issue` は今のまま。

### 6.7 インフラのリポジトリ

setup の調査で `*.tf` などからインフラのリポジトリと分かったもの、または人がインフラと指定したものは、次のように扱う（私の判断）。

- 自動で Done にしない。必ず In review にする。
- worker は `fmt` / `validate` のような、クラウドに触れない確認だけを走らせる。`plan` / `apply` やクラウドの認証情報を使う操作はしない。

### 6.8 環境の確認と並列数（`make setup`）

orca-team-dispatch-task に `make setup` を用意する。済んだ段は飛ばし、途中から再開できるようにする（slack-issue-intake の setup と同じ考え方）。

段の内容:

1. **事前確認**: node、gh、git、orca。
2. **拾う対象**: Issue を拾うリポジトリ（`owner/name`）と、拾う条件（既定はステータスラベル `Ready`）。
3. **関連リポジトリ**: 実装する可能性のあるリポジトリの組。各リポジトリについて、この PC の checkout の場所、`owner/name`、Orca への登録を確かめる。
4. **ラベル**: 拾う対象のリポジトリに、ステータスラベル 8 つが無ければ作る。
5. **sudo の扱い**: 「この環境で AI に sudo を許すか」を一度だけ聞く。既定は許さない。EC2 のように、パスワードなしで sudo が使える環境で許す想定。
6. **リポジトリごとの確認**: 下の「確認の手順」を行う。
7. **並列数**: 下の「並列数の判定」を行い、結果を見せて確定する。
8. **automation の登録**: 間隔を聞き、Orca の automation を無効の状態で登録する。
9. **有効化**: 権限の内容を見せ、承認されたら有効にする。

段の分け方と順番の細部は builder に任せる。

**確認の手順（リポジトリごと）**

1. Claude を一度起動し、CI の定義、`package.json`、`Makefile`、`go.mod`、`pyproject.toml`、`mise` / `.tool-versions`、`compose` のファイル、README などを読ませる。そこから、build / test / lint のコマンドと、必要な道具を割り出させる。言語やフレームワークを決め打ちしない。
2. 作業用の worktree で、そのコマンドを実際に走らせる。その間の最大メモリ使用量（Linux は `/usr/bin/time -v`、mac は `-l`）と、ディスクの増え方を測る。
3. 足りない道具の扱い（ユーザーの指示）:
   - **自動で入れられそうなものは AI が入れる**: すでにあるバージョン管理ツールやパッケージ管理ツール（`mise`、`asdf`、`nvm`、`brew`、`corepack`、`apt`（sudo を許した場合）など）で入れられるもの、リポジトリ内の依存パッケージ。入れたものは段の最後に一覧で見せる。
   - **入れられそうにないものは、人に何が足りないかを教える**: sudo が要る（許していない場合）、PC 全体の設定を変える、アカウントやライセンスが要る、秘密の値（`.env` など）が要るもの。何が足りないか、どのコマンドで使うか、入れ方の手がかりを見せる。人が入れたら、その段だけやり直せる。
4. 通ったコマンドと測った値を、リポジトリごとに記録する。通らなかったリポジトリは「確認できない」と記録する。そのリポジトリを含む Issue は In review に回す（6.6）。

**既定の道具**（ユーザーの指示: 既定である程度指定したい）

| 道具 | mac | Linux（EC2 など） |
|---|---|---|
| コンテナ | Rancher Desktop（`brew install --cask rancher`。初回の起動と権限の許可は人が行う） | Docker Engine（`docker-ce`。apt のため sudo を許した場合だけ自動） |
| ほか | `git`、`gh`、`jq`、`mise` | 同左 |

この表は設定で上書きできるようにする。Rancher Desktop は画面のある PC 向けで、画面のないサーバーでは使わない。Docker Engine と Rancher Desktop は Apache License 2.0 で、商用でも無料。Docker Desktop は大企業での業務利用が有料なので、既定にしない。Docker Hub は、ログインしていないと取得回数に上限があるので、ログイン状態を確かめ、していなければ注意を出す（私の判断）。

**並列数の判定**

OS から、メモリの総量と空き、swap、ディスクの空き、CPU 数を読む。EC2 のインスタンスタイプは参考として読むが、判定には使わない（メタデータが取れない環境があったため）。

```text
並列数 = min(
  (使えるメモリ − 予備) ÷ (Claude 1 つ分 + 測った build の最大メモリ のうち最大のもの),
  ディスクの空き ÷ 1 件分のディスクの増え方,
  CPU 数
)  ただし 1 以上
```

- 予備（OS と orca serve など）と Claude 1 つ分の値は、`defaults` に置く。値は builder が決める。
- swap が 0 なら注意を出す。sudo を許した環境では、swap ファイルを作るか聞く（私の判断）。
- 足りない場合は、swap を足す、ディスクを広げる、インスタンスを大きくする、といった提案を出す。
- 結果は推奨値として見せ、人が確定する。

同じ判定を `--issue` でも使い、一度に流す件数が推奨値を超えていれば注意を出す（ユーザーの指示）。

並列数は数値の設定になる。今の設定（`lib/config.ts` の `TOGGLES`）は文字列の選択肢しか扱えないので、数値の種類を足す。

## 7. ユーザーが決めたこと

- フォームはカテゴリごとの 3 つのボタンに分ける。項目は 4.2 の表のとおり。
- 投稿の項目名は太字、複数行の値は ``` で囲み、項目の間は空行で区切る。
- ステータスラベルは Backlog / Ready / Ready_Eng / In progress / In review / Pending / Done、これに Failed を足す。両方のプラグインで共通にする。
- 起票時は Backlog。人が Ready か Pending にする。AI は Ready だけを拾う。
- 難易度の高いものや新機能など、長時間かかりそうなものは Ready_Eng にして、`@グループ` にメンションする。
- 結果が明らかな修正は AI が Done にして `@グループ` に知らせる。AI が自分で判断した点があるものは In review にして `@グループ` に知らせる。
- Done は default ブランチへの PR を作ってから merge する。main 決め打ちにしない。
- In review の PR が merge されたのに Done になっていなければ、次の回で Done にして close する。
- critical はキューの先頭に入れる。
- 別の worktree で実装する。終わったらブランチを remote に push してから、worktree とローカルのブランチを消す。
- 実装するリポジトリは、setup で関連リポジトリの組として登録する（1 つの Issue が複数のリポジトリにまたがる）。
- メンションするグループは `make setup` で入力する。
- `make setup` で CPU とメモリから並列数を判定する。`--issue` でも推奨値を出す。
- 自動で入れられる道具は AI が入れ、入れられないものは何が足りないかを人に教える。既定の道具を指定できるようにする。
- 言語やフレームワークは決め打ちせず、汎用にする。
- `--auto` は `--issue` とは別のモードにする。
- 終わらない worker の上限時間は、難易度から AI が推奨値を決める。
- In review / Failed を人が Ready に戻したら、前のブランチと PR を引き継いで続きから行う。
- AI どうしのレビューは行う。ただし別のセッションにはせず、worker のセッションの中の subagent（対象リポジトリに `.claude/agents` があればそれ）で行う。

## 8. 私の判断（確認してほしい点）

- 古い投稿の形（`本文:`）も読み続ける。
- 1 つの Issue が複数のリポジトリにまたがるときは、1 人の worker がまとめて担当する。
- 対象リポジトリが 3 つ以上なら Ready_Eng にする。
- 優先度ラベルが無いものは middle と同じに扱う。
- critical でも、実装中のものには割り込まない。
- 人が In progress のラベルを変えたら、worker を止めて後片付けする。
- Failed でも `@グループ` にメンションする。
- Failed のブランチも、コミットがあれば push してから消す。
- インフラのリポジトリは自動で Done にせず、`plan` / `apply` もしない。
- CI が落ちたものは In review に回す。
- Slack への通知は slack-issue-intake の poll が行い、orca-team-dispatch-task は Slack を知らない。2 つは Issue のラベルとコメントのマーカーでつながる。
- `--issue` の除外条件に、古い `dispatch/*` を残す。
- sudo は既定で許さない。setup で一度だけ聞く。
- Docker Hub のログイン状態を確かめる。swap が 0 なら注意を出す。
- `--auto` の worker は新しい形にする（1 件 1 人、結果をファイルに書いて終わる）。
- `.claude/agents` が無いリポジトリでは、組み込みの汎用 subagent でレビューする。解消しなかった指摘と採らなかった指摘は In review に回す。
- `--auto` を設定したリポジトリでは、`--issue` は Ready も拾わない。
- 人が merge した PR を見て AI が Done にしたときは、メンションしない。
- 複数リポジトリの merge が途中で失敗したら In review にする。
- 前からある `from-slack` の Issue にはさわらず、最初の poll では通知しない。
- 上限時間を超えたら止めて Failed にする。進みが無いときは、止めずに 1 回だけ知らせる。
- Ready に戻された前の PR が閉じられていたら、ブランチから新しい PR を作る。

## 9. builder に任せること

- ボタン、フォームの題、通知の文言。
- ステータスラベルの色と説明。
- コメント本文の書式（マーカーの形は 5.4 のとおり）。
- 状態ファイルとロックの形。
- 判定に使う model と effort の既定値。
- 予備のメモリと Claude 1 つ分のメモリの値。
- merge のやり方の選び方。
- 複数の worktree を 1 人の worker に渡す方法。
- `make setup` の段の細かい分け方。
- 各部分のテストの置き方。プラグインの CLAUDE.md にある決まり（正本先行、SKILL.md の bash に判定を書かない、英語の指示文書と `*-ja.md` の訳、maskSecrets、締め切り）に従う。
