# Issue の自動消化への追加 設計（複数リポジトリ・複数サーバー・定期報告・レビューモード）

日付: 2026-11-13
対象: `apps/orca-team-dispatch-task`（部分 C2 / C3）、`apps/slack-issue-intake`（部分 B の拡張。以下「B2」）
元の設計: `docs/superpowers/specs/2026-11-12-issue-auto-dispatch-design.md`（以下「元の設計」）。この文書は、元の設計の 6 章（部分 C）と 5 章（部分 B）に足すもの・変えるものだけを書く。書いていない点は元の設計のとおり。

## 1. 目的

ユーザーは複数の organization・リポジトリの修正を同時に進めている。対象が多く、1 つのタスクが backend と frontend のように別のリポジトリに分かれることもある。そのため、次の 4 つを実現したい。

- 複数の organization・リポジトリのタスクのキューを、1 か所で同時に把握する。
- 空いているマシンのリソースを遊ばせず、空いていればどんどん並列で回す。
- 今どれだけキューに溜まっていて、何が実行中かを、定期的に Slack で知る。
- `--auto` でも、必要ならレビュー役の worker によるレビューを使う。

## 2. 元の設計から変わること（要約）

| 項目 | 元の設計 | この設計 |
|---|---|---|
| Issue を拾うリポジトリ | 1 つ（slack-issue-intake の起票先）。複数は非目標 | 複数。別の organization も可。キューは 1 本にまとめる |
| slack-issue-intake の起票先 | 1 リポジトリ | 受け付けるリポジトリの一覧と、既定の起票先 |
| Slack から作っていない Issue | 扱わない | スレッドを作って管理するか、対象外にするかを setup で選ぶ |
| ステータスを変える場所 | ラベル | ラベル。GitHub Project を使うリポジトリでは、Project の Status とラベルを両方向で揃える |
| worker を動かすマシン | 親と同じマシン | Orca につながっている複数のマシン（この Mac、ペアリング済みのサーバー、SSH の接続先）。空いている所へ振り分ける |
| 1 件の進め方 | 1 人の worker（計画も実装も）。レビューはセッション内の subagent | `--issue` と同じ役の組み合わせ（design / design_review / exec / exec_review）を setup の `review_mode` と `phase_b` で選ぶ。どちらも off なら 1 人で、レビューはセッション内の subagent |
| Slack への定期報告 | なし | キューと実行中の一覧を、1 つの投稿の書き換えと 1 日 1 回の新しい投稿で知らせる |
| 非目標「orca-team-dispatch-task から Slack へ直接投稿しない」 | — | 変えない。定期報告も slack-issue-intake が投稿する |

## 3. 決めたこと（ユーザーが決めたこと）

- Issue を拾うリポジトリは複数にでき、別の organization も可。
- 複数のマシンへの振り分けは「親が 1 つ」の形（下の「4. 作り方の比較」の A）。親がキューとすべての Issue の状態を持ち、起動のたびに各マシンの空きを Orca に聞いて、空いている所へ dispatch する。各マシンには worker だけを置く。
- `--auto` の親と slack-issue-intake は同じマシンで動かす前提。
- Slack のフォームの起票先:
  - setup で、受け付けるリポジトリの一覧と、既定の起票先を決める。
  - 一覧が 1 つだけなら、フォームにリポジトリの欄を出さない（複数のリポジトリにまたがる作業でも、Issue を 1 か所で管理している場合）。
  - 2 つ以上なら、リポジトリの選択欄を出す。ただし任意で、空なら既定の起票先にする（エンジニア以外も起票するため）。
- Slack から作っていない Issue も管理できるようにする。スレッドの無い Issue を見つけたら、スレッドを作るか、スキップして対象外にするかを選べる。
- GitHub Project を使う場合、人が Project で Status を変えたらラベルも変わり、ラベルを変えたら Project の Status も変わる（両方使える）。
- `--auto` でもレビューモードを有効にでき、`--auto` の setup で聞く。1 件の進め方は 1 人ではなく、`--issue` と同じ動き（役の組み合わせ）ができるようにする。
- Slack から作っていない Issue の扱い（スレッドを作る / 対象外）は、リポジトリごとに決める。
- Slack の定期報告は「両方」: 普段は 1 つの投稿を書き換え続け、1 日 1 回は新しい投稿にする。

## 4. 作り方の比較（複数マシンへの振り分け）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. 親が 1 つ（採用）** | 親がキューを持ち、起動のたびに各マシンの worktree の数を Orca に聞いて空きへ dispatch。マシンには worker だけ | 単純。二重に拾わない。空いた所へ詰めるので目的を満たす | 親のマシンが止まると新しい dispatch も止まる（動いている worker は止まらない）。遠くのマシンの空きメモリは毎回は測らず、setup で決めた上限に頼る |
| B. 親 ＋ 各マシンのキュー管理役 | 親が各マシンのキューへ割り当て、管理役がその場の空きを見て起動し、状態を返す | その場の空きを細かく見られる。親が止まっても割り当て済みは進む | 状態が 2 段になり、食い違いの処理が増える。マシンごとに automation がもう 1 つ要る |
| C. 各マシンが GitHub から直接拾う | 親を置かない | 単一障害点が無い | 「親が全体を管理する」に合わない。二重取得の調停が難しい |

ユーザーは A を選んだ。

## 5. 複数のリポジトリ（C2・C3）

### 5.1 登録の単位

`--auto` の setup で、**拾う元のリポジトリ**（`owner/name`。organization は混在可）を複数登録する。拾う元ごとに、次の 3 つを持つ。

- **関連して実装するリポジトリの組**（元の設計 6.8 の 3 段目）。拾う元自身を含めてもよい。難易度の判定（元の設計 6.3）では、AI がこの組の中から実際に触るリポジトリを選ぶ。
- **GitHub Project**（任意）。`owner` と Project の番号。5.4 を参照。
- 拾う条件（既定は `Ready` のラベル。元の設計 6.8 の 2 段目）。

実装するリポジトリは、別の拾う元の組と重なってもよい。リポジトリごとの確認の情報（確認コマンド、必要な道具、インフラかどうか）は、リポジトリ単位で 1 回だけ持つ（私の判断）。

### 5.2 キュー

- すべての拾う元をまとめて 1 本のキューにする。並び順は元の設計 6.4 のとおり（優先度の高い順、同じ優先度なら Ready になった古い順、critical は先頭）。拾う元の違いで順番は変えない。
- Issue はどこでも `owner/repo#番号` で呼ぶ。状態ファイル、ロック、ブランチ名、worktree の名前、マーカーのコメントの中も同じ。番号だけで呼ぶ所を残さない（別のリポジトリで番号が重なるため）。
- ステータスラベル 8 つは、拾う元のすべてのリポジトリに作る（C1 の `ensure-labels` と同じ）。

### 5.3 管理の対象にする Issue

`--auto` が拾うのは、**slack-issue-intake が管理している Issue だけ**にする（私の判断。2 つのプラグインの約束）。「管理している」の印はラベルで表す。

- `from-slack`: Slack のフォームから起票した Issue（今のまま）。
- `slack-thread`（新しく作る）: Slack から作っていない既存の Issue に、slack-issue-intake がスレッドを作って管理に入れたもの。

slack-issue-intake の「既存の Issue」の設定（B2 の 7.3）が「対象外にする」なら、`slack-thread` は付かないので、`--auto` も拾わない。これで「スキップして対象外にする」と「スレッドを作って管理する」の両方が、ラベル 1 つの約束で表せる。

### 5.4 GitHub Project の Status とラベルの同期

- GitHub の Project は持ち主（organization か個人）のリポジトリを扱う。別の organization をまたぐ場合は、organization ごとに Project を登録する（拾う元ごとに任意の Project を持てる形なので、そのまま扱える）。organization の Project が別の organization のリポジトリの Issue を持てるかは未確認。
- 同期は `--auto` の親が、起動のたびに行う。対象は、Project を登録した拾う元の Issue のうち、その Project に入っているもの。
  - Project の Status だけが前回から変わっていれば、ラベルを付け替える。
  - ラベルだけが変わっていれば、Project の Status を動かす。
  - 両方が変わっていれば、変えた時刻があとのほうに合わせる。時刻は GitHub の記録（Project の項目の Status の更新時刻、Issue のラベルの付け外しの時刻）から取る。
- 前回の値は、親の状態ファイルに Issue ごとに持つ。
- 反映は起動の間隔ぶん遅れる。親が止まっている間は揃わず、再開した最初の回にまとめて揃える。
- Project に入っていない Issue は、ラベルだけで動く。
- setup の確認:
  - Project の Status の選択肢に、ステータス 8 つがあるか。無ければ足す。名前は大文字小文字を区別せずに比べる。
  - gh に `project` の権限があるか。無ければ `gh auth refresh -s project` を案内する。
- `--auto` 自身がラベルを動かすとき（In progress、In review、Done など）も、同じ回で Project の Status を揃える。
- 部分 B の通知（slack-issue-intake）は今のとおりラベルを読む。Project で変えた変化は、同期のあとに通知される。

## 6. 複数のマシン（C2・C3）

### 6.1 対象のマシン

Orca の `orca host list` が返すもののうち、setup でユーザーが選んだもの。

| 種類 | 例 | Orca での指定 |
|---|---|---|
| この Mac | this machine | `--host local`（または指定なし） |
| ペアリング済みのサーバー | Mac M2max、EC2 の `orca serve` | `--environment <名前>`（worker-start は `--on <名前>`） |

SSH の接続先は対象にしない（9 章の非目標）。

親は今の Mac で動く。worker はどのマシンでも動く。

### 6.2 setup でマシンごとに行うこと（C3）

1. **接続の確認**: そのマシンへの `orca status` が通るか。通らなければ、その旨を示してそのマシンを外すか聞く。
2. **スペックの測定**: そのマシンで短いコマンドを走らせ、CPU 数、メモリの総量と空き、swap、ディスクの空きを測る。Orca はこれらを返さないので、Orca の端末を作ってそこで node の 1 行を走らせる（そのマシンに node が必要）。測った値は親の設定に保存する。
3. **リポジトリの置き場所**: 実装するリポジトリごとに、そのマシンでの checkout の場所を確かめ、Orca に登録されていなければ登録する（`orca repo add --environment ...`）。無いものは、clone するか、そのマシンではそのリポジトリを扱わないかを聞く。
4. **gh と git の認証**: そのマシンの gh がログイン済みで、push できるか。
5. **リポジトリごとの確認**（元の設計 6.8 の「確認の手順」）: マシンごとに行う。道具の有無や確認コマンドの結果はマシンによって違うため。
6. **最大の並列数**: 元の設計 6.8 の式を、そのマシンの測った値で計算して推奨値として見せ、人が確定する。

あるリポジトリの確認が通っていないマシンには、そのリポジトリを含む Issue を振り分けない。

### 6.3 振り分け（C2）

親は起動のたびに、マシンごとに次の順で行う。

1. そのマシンに到達できるかを確かめる。できなければ、この回はそのマシンを使わず、定期報告に「つながらない」と出す。
2. そのマシンで動いている `--auto` の worktree の数を、`orca worktree list` で数える。`--auto` が作った worktree は名前の接頭辞で見分ける。
3. 空き = そのマシンの最大の並列数 − 動いている worktree の数（8.3）。最大の並列数も worktree の数で持つ。
4. キューの先頭から、その Issue の対象リポジトリがすべて確認済みのマシンを選んで入れる。候補が複数あれば、空きの割合が大きいマシンを選ぶ（builder に任せる）。

元の設計 6.5 の「レーンに入れる直前に、空きメモリと空きディスクを確かめる」は、この Mac では今のとおり行う。遠くのマシンでは毎回は測らず、setup で決めた最大の並列数に頼る（A の短所として受け入れた）。

### 6.4 worker との受け渡し

worker は別のマシンで動くことがあるので、親はそのマシンのファイルを直接読めない。元の設計 6.5 の「結果をファイルに書いて終わる」は、次のように受け渡す。

- worker は、終わりの報告（AI が決めた点の一覧、リポジトリごとの PR と merge の順番、失敗の理由）を、`--issue` と同じく Orca の orchestration のメッセージ（`merge_ready` / `worker_done`）で親の Run に送る。親は次の起動でそれを読む（8.2）。
- 進みが止まっているかの判定（元の設計 6.5 の「終わらない worker」）は、worker のブランチの remote への push と、Orca の worker の状態から読む（builder に任せる）。

## 7. slack-issue-intake の拡張（B2）

### 7.1 受け付けるリポジトリ

- setup で、受け付けるリポジトリの一覧（`owner/name`、organization は混在可）と、既定の起票先を決める。
- 一覧が 2 つ以上なら、3 つのフォームそれぞれに「リポジトリ」の選択欄（任意）を足す。選択肢は一覧。空なら既定の起票先。一覧を変えたら `make setup` でフォームを作り直す。
- Issue の番号はリポジトリごとなので、DB は Issue を `(リポジトリ, 番号)` で持つ。部分 B の `issue_status` も同じ。今の DB からの移し替えでは、今の 1 リポジトリを入れる。
- ステータスの通知（部分 B）は、受け付けるリポジトリすべてを読む。
- ラベル（`from-slack`、`slack-thread`、ステータス 8 つ、カテゴリ、優先度）は、受け付けるリポジトリすべてに作る。

### 7.2 定期報告

- `--auto` の親は、起動のたびに、報告の材料を JSON で親の状態のディレクトリに書く。中身は次のとおり。
  - 実行中の Issue（`owner/repo#番号`、題名、マシン、経過時間、上限時間）
  - キュー（順番、優先度、`owner/repo#番号`、題名）
  - マシンごとの空き（動いている数と最大）と、つながらないマシン
  - 書いた時刻
- slack-issue-intake の poll がそれを読み、報告のチャンネルに投稿する。
  - 普段は、1 つの投稿を書き換え続ける（`chat.update`）。投稿が消されていたら、新しく投稿し直す。
  - 1 日 1 回、決まった時刻を過ぎた最初の poll で、新しい投稿をする。以後はそれを書き換える。
- 報告のチャンネルは、既定では起票と同じチャンネル。setup で別のチャンネルにできる。1 日 1 回の時刻も setup で決める（既定は 9 時）。
- 材料の JSON の置き場所は、2 つのプラグインの約束にする。既定は `~/.claude/config/orca-team-dispatch-task/auto/<名前>/report.json`。slack-issue-intake は、setup で見つけた（または指定された）置き場所を config に持つ。
- 材料が古い（親が止まっている。目安は確認の間隔の 3 倍）ときは、報告に「`--auto` が止まっています（最後の更新 …）」と出す。
- 例:

```text
📋 自動実行の状況（11/13 14:30）
実行中 3件
  • orgA/app#42 ログインできない … Mac M2max・35分 / 上限60分
  • orgB/api#7 CSV 出力 … EC2・12分 / 上限90分
キュー 4件
  1. [critical] orgA/app#51 決済が落ちる
  2. [high] orgB/api#9 …
空き: Mac M2max 0/2・EC2 1/3・この Mac 1/2
```

### 7.3 Slack から作っていない Issue

- setup で、受け付けるリポジトリ**ごとに**、開いている Issue のうち `from-slack` も `slack-thread` も付いていないものの扱いを選ぶ（ユーザーの決定）。
  - **スレッドを作る**: ボットが起票のチャンネルに「この Issue を管理に入れました」という投稿（題名、`owner/repo#番号`、URL、今のステータス）を立て、`slack-thread` を付けて管理に入れる。以後の通知はそのスレッドに書く。
  - **対象外にする**: 何もしない。`--auto` も拾わない（5.3）。
- setup の時点だけでなく、poll の毎回でも新しい対象を探す（あとから GitHub で直接作られた Issue のため）。
- setup の時点ですでに開いている古い Issue には、ステータスラベル（8 つのどれか）が付いたものだけスレッドを立てる。付いていない古い Issue は、ステータスラベルが付いた時点で対象にする。setup のあとに作られた Issue は、ラベルが無くても対象にする（私の判断。数百件の古い Issue で Slack が埋まらないように）。
- 一度に大量のスレッドが立たないよう、1 回の poll で立てる数に上限を設ける（値は builder に任せる）。
- 管理に入れた時点では通知を出さない（部分 B の「前からある Issue」と同じ）。

## 8. 1 件の進め方とレビューモード（C2・C3）

### 8.1 役の組み合わせ（ユーザーの決定）

`--auto` の 1 件は、`--issue` と同じ役の組み合わせで動く。`--auto` の setup で `review_mode` と `phase_b` を聞き、`--auto` の設定に持つ。

| review_mode | phase_b | 役 | 1 件の worktree |
|---|---|---|---|
| off | off | design（計画と実装。レビューはセッション内の subagent。元の設計 6.5） | 1 |
| on | off | design、design_review（計画のレビュー） | 2 |
| off | on | design（計画）、exec（実装） | 2 |
| on | on | design、design_review、exec、exec_review（実装のレビュー） | 4 |

複数のリポジトリにまたがる Issue は、役ごとにリポジトリの数だけ worktree を持つ（1 つの役が複数の worktree を担当する。渡し方は元の設計のとおり builder に任せる）。

### 8.2 待ち続ける親がいないことへの対応（私の判断。計画の最初に小さく試して確かめる）

`--issue` の役は、親が端末で待ち続けて、worker の差し出し（`merge_ready`）を受理し、計画が終わったら exec を起こす、という二段の完了に頼っている。`--auto` の親は数分おきに起動してすぐ終わるので、次のようにする。

- 親は起動のたびに、`--issue` の待機（`orca-wait.ts`）と同じ処理を **1 歩ぶん** 進める。届いている `merge_ready` を確かめて受理か差し戻しを返し、計画が終わった件の exec を起こし、決着した件を仕上げ（元の設計 6.6）へ回す。待ち続けはしない。受理や次の役の起動は、確認の間隔ぶん遅れる。
- Orca では Run を「まとめ役の端末」が持つ必要がある（今の `orca-start.ts` は `ORCA_TERMINAL_HANDLE` を Run の coordinator にする）。この Mac に `--auto` 用のまとめ役の端末を 1 つ開いたままにし、親は起動のたびにその端末の handle で Run を操作する。
  - これが Orca で成り立つか（ほかのプロセスがその handle で `check` / `send` / `worker-start` を打てるか、端末が閉じたときにどう戻すか）は未確認。C2 の最初のタスクで小さく試し、成り立たなければ別の方法を探す。
- 遠くのマシンの worker も、同じ Run（この Mac のまとめ役）に属する。

### 8.3 空きの数え方

6.3 の「空き」は、Issue の数ではなく、**動いている `--auto` の worktree の数**で数える。1 件で使う worktree は 8.1 の表のとおり 1〜4 つ（複数リポジトリならさらに増える）。次に入れる Issue が使う worktree の数が空きを超えるマシンには入れない。

## 9. 目標・非目標・してはいけないこと（追加分）

目標:

- どのリポジトリの Issue も、1 本のキューの優先度の順で処理される。
- つながっているマシンに空きがある限り、キューは止まらない。
- 定期報告を見れば、キュー、実行中、マシンの空きが分かる。

非目標:

- 親を複数置くこと（親の冗長化）。親が止まっている間、新しい dispatch は止まる。
- 遠くのマシンの空きメモリを、dispatch のたびに測ること。
- SSH の接続先で worker を動かすこと（Orca の `worker-start` が遠くのマシンを選ぶ口はペアリング済みのサーバー `--on <environment>` だけのため）。
- 別の organization の Issue を 1 つの GitHub Project にまとめること（organization ごとに Project を登録する）。

してはいけないこと:

- 同じ Issue を 2 つの worker に渡す（`owner/repo#番号` で一意にする）。
- 番号だけで Issue を呼ぶ（別のリポジトリの Issue と取り違える）。
- 確認が通っていないマシンに、そのリポジトリの作業を振り分ける。
- 管理の対象外にした Issue（7.3）を拾う。
- 人が Project かラベルで変えたステータスを、同期で古い値に戻す。

## 11. 私の判断（確認してほしい点）

- 確認が通っていないリポジトリを含む Issue: 確認が通っているマシンを優先する。どのマシンでも通っていなければ、checkout のあるマシンで実装し、merge せず In review に回す（元の設計 6.6 のまま）。6.2 末尾の「振り分けない」は「通っているマシンがあれば、通っていないマシンには振り分けない」と読む。
- Project の Status が 8 つ以外（`Todo`、空など）のときは、ラベルを変えない。GitHub の組み込みの workflow（追加したら Todo など）は、setup で止めるよう案内する。組み込みの workflow が変えた値も、人の変更と区別できないので同じに扱う。
- Project の同期の対象は、管理している Issue（`from-slack` / `slack-thread`）だけ。
- `--auto` が拾う元の一覧は、slack-issue-intake の受け付けるリポジトリの一覧をそのまま使う（同じマシンなので、正本を 1 つにする）。フォームに出したくないリポジトリは、一覧の項目に「フォームに出さない」の印を持たせる。
- worker が動いているマシンにつながらなくなったら、ほかのマシンでやり直さずに待つ（二重に動かさないため）。定期報告に出し、上限時間を過ぎたら一度だけ `@グループ` に知らせる。つながりが戻ったら、元の設計 6.5 の上限時間の処理をする。
- `--auto` の worker は、`orca`・`gh`・`git` だけで完結させ、遠くのマシンにこのプラグインを入れなくても動くようにする（今の worker の指示は親のマシンのプラグインのパスを呼ぶため）。

- リポジトリごとの確認の情報は、リポジトリ単位で 1 回だけ持つ。拾う元の組が重なっても、確認は重ねない。マシンが違えば、マシンごとに持つ。
- `--auto` が拾うのは、slack-issue-intake が管理している Issue（`from-slack` か `slack-thread` が付いたもの）だけにする。
- 両方が変わっていたときの同期は、あとから変えたほうに合わせる。
- 遠くのマシンへの振り分けでは、毎回の空きメモリの測定をせず、setup の最大の並列数に頼る。
- worker の終わりの報告は、Orca の orchestration のメッセージで親へ送る（遠くのマシンのファイルを読めないため）。
- 報告のチャンネルは既定で起票と同じ。1 日 1 回の投稿は既定で 9 時。
- 材料が古いときは、報告に「止まっています」と出す。
- 1 回の poll で立てるスレッドの数に上限を設ける。

## 12. builder に任せること

- 報告の材料の JSON の形（中身は 7.2 のとおり）と、投稿の文言。
- 1 日 1 回の投稿の時刻の持ち方、書き換える投稿の ts の持ち方。
- 空きの割合でマシンを選ぶときの細かい規則。
- スペック測定のコマンドの細部と、測定に使う Orca の端末の片付け方。
- 1 回の poll で立てるスレッドの上限の値。
- 進みの判定に使う材料（push、Orca の worker の状態など）の組み合わせ。
- `--auto` が作る worktree の名前の接頭辞。
- C2 の計画の分け方。
