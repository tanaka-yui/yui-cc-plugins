# 判定の学び（--auto の判定を結果から改善する）

## 目的と理由

`--auto` の判定（自動で進めるか、エンジニアに回すか。Backlog の Issue を Ready にするか）は、今はプラグインに入っている固定の文章 1 つ（`skills/orca-team-dispatch-task/references/auto-judge.md`）だけで決まる。リポジトリごとの事情は持たず、判定とその後の結果の履歴も残らない（Issue を閉じると状態の記録ごと消える）。

本格運用はこれからで、「できるはずの Issue をエンジニア行きにしてしまう」などの食い違いが出たときに、精度を上げていく仕組みを先に用意しておく。学びの行き先は 2 つある。

- リポジトリ固有の学び: その端末にためて、次の判定から自動で効かせる。Slack に「XXXX に関するところは、今後こう判定します」と知らせる。
- 全体に効く学び: yui-cc-plugins の判定の文章を直す改善として出し、Slack に「改善の PR を作りました」と知らせる。merge するのは人。

## ゴール・非ゴール・失敗とみなすこと

- ゴール: 判定と結果を Issue ごとに記録し、食い違いがたまったら AI が振り返って、リポジトリごとの短い規則を作る。規則と似た過去の事例を、次の判定の材料に足す。
- ゴール: 学びを Slack に知らせ、Slack から取り消せる。
- ゴール: setup で「はい」と答えた端末では、全体に効く学びを yui-cc-plugins の改善の Issue にする。その Issue は、yui-cc-plugins を拾う元にしている `--auto` が、いつもの流れで PR にする。
- 非ゴール: ベクトル検索（埋め込み）。実行時に追加のライブラリを入れない作りに合わず、1 リポジトリの Issue は数十〜数百件なので語の重なりで足りる。事例の選び方は後で差し替えられる形にする。
- 非ゴール: AI がリポジトリごとの判定の文章を自由に書き直すこと。
- 非ゴール: 判定の AI に新しい権限を渡すこと（許可するコマンド・書けるファイル・権限の指紋を変えない。変えると、更新のあと全員が `make auto-setup` で承認し直すまで tick が止まる）。
- 失敗とみなすこと:
  - 学びで「自動で進める範囲」が広がり、人が一度も見ないまま AI が merge すること（下の「様子見」で防ぐ）。
  - 判定の基準そのものを変える PR を、AI が merge すること。
  - 非公開のリポジトリの名前・Issue の番号・題名・本文が、公開リポジトリ（yui-cc-plugins）の Issue や PR に出ること。
  - Issue の本文に書かれた文が、規則を通って判定への指示として働くこと。
  - 1 件だけの出来事で規則ができること。

## 選んだ形（Approaches）

- A（採用）: 決まった形の短い規則の一覧と、過去の事例を判定に渡す。規則が決まった形なので、検査・取り消し・「この規則で自動になった Issue は最初の数件だけ人の確認」の対応付けができる。
- B（不採用）: リポジトリごとの判定の文章を AI が全文書き直す。書き直すたびに中身がずれ、どの文がどの Issue に効いたかを追えず、取り消しも前の版に戻すしかない。
- C（不採用）: 過去の Issue をベクトル検索する。上の非ゴールのとおり。

人が決めたこと:

- 広げる学び（自動で進める向き）も自動で効かせる。ただしその学びで自動になった Issue は、最初の数件だけ PR を人の確認に回す（様子見）。
- 全体に効く学びは、改善の Issue を yui-cc-plugins に作り、いつもの流れで PR にする（振り返りの AI が直接 PR を作らない）。
- 「改善の Issue を作る」と「拾って実装する」を分ける。setup では Issue を作るかだけを聞く（書き込める端末なら何台でも「はい」にできる）。実装するのは yui-cc-plugins を拾う元に入れた端末で、これは今の拾う元の設定のまま、1 台だけにする運用とする（今の `--auto` には、同じ Issue を複数の端末で取り合わない仕組みが無いため）。
- 学びは、Backlog からの auto-ready の判定にも、人が Ready にした Issue の「自動かエンジニアか」の判定にも効かせる。

## 全体の流れ

```
判定 ──→ 実行 ──→ 結果（merge・人の確認・失敗・人が止めた・人が戻した）
  ↑                    │
  │                    ↓ tick が履歴に 1 行足す（AI は使わない）
  │               履歴（端末・リポジトリごと）
  │                    │ 食い違いが 3 件たまったら
  │                    ↓
  │               振り返り（判定と同じ AI の起動に相乗り）
  │                    │ 規則の案（決まった形の JSON）
  │                    ↓ CLI が検査して保存
  └── 規則＋似た事例 ←─ 規則（端末・リポジトリごと）──→ Slack に知らせる（取り消しは返信）
                             │ 様子見を終えた規則のうち、全体に効くもの
                             ↓
                        yui-cc-plugins の Issue（一般化した文だけ）→ --auto → PR → 人が merge
```

## 決まったこと

### 1. 履歴（orca）

- 置き場所は `--auto` の設定フォルダの下（`auto/<name>/learn/`）。プラグインのフォルダには置かない（更新で入れ替わるため）。
- Issue の 1 世代が終わるたびに、tick が 1 行を足す。AI は使わない。1 行の中身: Issue の key、世代、題名、ラベル、AI の判定（`auto` / `eng`）、実際に効いた向きと CLI が向きを変えた理由（新機能・3 リポジトリ以上など。無ければ空）、判定の理由、auto-ready かどうか、判定が頼った規則の id、結果、時刻。本文は入れない。
- 結果の種類:
  - `merged-ai`（AI が merge した）
  - `merged-human`（人の確認に回り、人が merge した）
  - `failed`（失敗・時間切れ。判定が原因になりうるもの）
  - `failed-env`（環境が原因の失敗。結果の報告の `envFailure`、つながらない遠くのマシン、起動の失敗、役の間の中継の待ちによる時間切れ）
  - `stopped`（人が止めた、人が Backlog などへ戻した、PR を merge せずに閉じた）
  - `eng-kept`（エンジニア行きのまま閉じた、または動かなかった）
  - `eng-returned`（エンジニア行きにしたが、人が自動に戻した。次の世代の結果とつないで読む）
- 食い違いとみなすもの:
  - 慎重すぎた: `eng-returned` のあと、次の世代が `merged-ai` か `merged-human`。
  - 攻めすぎた: AI の判定が `auto` で、結果が `failed` か `stopped`。
- 食い違いに数えないもの:
  - `failed-env`（判定の誤りではない）。様子見の規則も、これでは取り下げない。
  - CLI が向きを `eng` に変えた Issue（AI の判定に関係なくエンジニア行きになる新機能・3 リポジトリ以上）。規則を作っても CLI に上書きされて効かないため。
- 履歴はリポジトリごとに新しい 500 件まで持ち、古いものから捨てる。
- 今は Issue を閉じると状態の記録を消している。消す前に履歴へ書く。

### 2. 振り返り（orca）

- リポジトリごとに、まだ振り返っていない食い違いが 3 件以上あれば、振り返りを 1 回行う。
- 振り返りは、判定の AI の起動に相乗りする。tick は、判定待ちの Issue が無くても振り返りが要れば AI を起こす。`judge-list` の出力に振り返りの材料（そのリポジトリの食い違いの行、今の規則）を足し、AI は今の判定結果のファイルに規則の案も書く。`judge-apply` が案を検査して保存する。新しいコマンド・新しく書けるファイルは足さない。
- 案の種類は 3 つ: 規則を新しく作る、今の規則に根拠を足す（同じ傾向の新しい食い違いが出たとき）、今の規則を取り下げる（その規則で攻めすぎた結果が出たときなど）。
- 新しい規則の案 1 件の形: 向き（`auto` / `eng`）、対象を表す短い文（日本語、80 文字まで、1 行）、根拠の Issue の key（その振り返りの材料にあるものだけ、2 件以上）。
- CLI の検査: 形が合うこと、根拠が材料にある食い違いの key であること、文に URL・コードブロック・改行が無いこと、同じリポジトリの有効な規則が 20 件を超えないこと（超えるなら案を捨てて 1 行出す）。
- 規則は、判定の指示としてではなく「過去の結果から分かった傾向」という材料として扱わせる。判定の文章（`auto-judge.md`）にその旨を書く。

### 3. 判定での使い方（orca）

- `judge-list` は Issue ごとに、そのリポジトリの有効な規則と、似た過去の事例を 5 件まで付ける。事例は履歴から、題名とラベルの語の重なりが多い順に選ぶ（題名・判定・結果だけ。本文は無い）。選び方は 1 つの関数にまとめ、後で差し替えられるようにする。
- 判定の AI は、`auto` にした Issue ごとに、頼った `auto` 向きの規則の id の一覧を判定結果に必ず書く（頼っていなければ空の一覧）。`judge-list` がその Issue に様子見の残っている規則を見せたのに、この項目が無い判定は、`judge-apply` が受け付けない（書き忘れで様子見を素通りさせないため）。

### 4. 様子見（orca）

- `auto` 向きの規則は、できた時点で「様子見の残り 3 件」を持つ。
- 判定結果が、様子見の残っている規則の id を挙げた Issue は、ほかの条件がそろっても AI が merge せず、PR を人の確認に回す（理由の 1 行: 「新しい学びで自動にした Issue なので、merge の前に人が確認します」）。
- その Issue を人が merge したら、残りを 1 減らす。0 になったら普通の扱いに戻す。
- その Issue が `failed` か `stopped` で終わったら、その規則を取り下げ、Slack に知らせる。
- `eng` 向きの規則に様子見は無い（安全側のため）。
- 残る弱点: AI が、頼った規則を「頼っていない」と書けば様子見を通らない。CLI は Issue と規則の対応を自分では判断できないため、ここは AI の申告に頼る。

### 5. 知らせと取り消し（orca と intake）

- orca は、学びの出来事（規則ができた・根拠が増えた・取り下げた・様子見を終えた・全体の改善の下書きができた・全体の改善の Issue を作った・その Issue の PR ができた）を、知らせの材料のファイルに書く。intake はそれを読み、定期報告のチャンネルにトップレベルの投稿を 1 つ作る（定期報告が無効なら投稿しない。orca の tick の出力には常に 1 行出す）。
- 投稿の形（例）:

```
🧠 判定の学び（acme/app）
1. 文言だけの修正は、今後は自動で進めます（最初の 3 件は人が確認します）
   根拠: #41 #52 #60
2. DB のマイグレーションを含む Issue は、今後はエンジニアに回します
   根拠: #47 #55
取り消すときは、このスレッドに「取り消し 1」と返信してください
```

- 取り消せる人は絞らない（そのチャンネルに書ける人なら誰でも）。取り消しは、判定をプラグインの元の基準に戻すだけのため。
- 取り消し: intake がその投稿のスレッドの返信を読み、「取り消し <番号>」を見つけたら、自分のホームのファイルに取り消しの依頼を書く。orca は次の tick でそれを読んで規則を取り下げ、intake がスレッドに「取り消しました」と返す。AI は起こさない。
- 2 つのプラグインは互いのファイルを書かない。orca は自分の設定フォルダに知らせの材料を書き、intake は自分のホームに取り消しの依頼を書く。形は両方の `test/fixtures` に同じ写しを置き、`scripts/check-shared-contracts.mjs` で照合する（今の報告の材料と同じやり方）。
- 端末だけでも見られるように、今ある `status` に規則の一覧を出す。

### 6. 全体に効く学び（orca）

- setup に質問を 1 つ足す: 「判定の学びを、yui-cc-plugins の改善の Issue として出しますか」。gh のアカウントに書き込む権限が無ければ、「はい」を選べない。答えは設定に残す。この質問は拾う元を変えない。
- yui-cc-plugins を拾う元に入れるかは、今の拾う元の設定で決める。setup は「同じリポジトリを拾う `--auto` は 1 台だけにしてください」と 1 行出す。どの端末も拾う元に入れていなければ、改善の Issue は Ready のまま残る（人が手で実装するか、あとで 1 台に足す）。
- 「はい」の端末では、振り返りの AI が「この規則はリポジトリ固有でなく、全体に効く」と判断した規則を、改善の案として出せる。条件: その規則が様子見を終えていること（`eng` 向きなら根拠が 5 件以上）、同じ規則をまだ出していないこと。
- CLI は、案の題と本文を検査してから下書きにする。本文は一般化した規則と件数だけ。検査: 設定にあるリポジトリ名を含まない、`#数字`・URL を含まない、長さの上限。検査に落ちたら作らず、tick に 1 行出す。
- **公開の前に人が全文を読んで承認する（実装の途中で足した段）。**検査を通った案でも、すぐには yui-cc-plugins に Issue を作らない。題と本文を下書きとして規則に残し、学びの知らせ（下書き）に載せる。人が承認するまで、その件では GitHub に何も送らない（Issue もラベルも作らない）。
  - 足した理由: 出す先は公開リポジトリで、題と本文は AI が書く。最初は検査だけで出す作りにしたが、自動のセキュリティレビューが検査のすり抜けを 4 回続けて見つけた。残る抜け道（語の一部の短い名前・owner だけ・区切り違い・設定の一覧に無い名前・GitHub の表示で名前になる綴り・NFKC で揃わない文字・符号化）は、言葉の検査では塞げない。言い換えや符号化した漏れは、人が読むほかに止めようがなく、公開リポジトリへの漏れは取り消せない。検査は一次の網として残し、下書きを作るときと公開するときの両方で掛ける（設定が変わっているかもしれないため）。
  - 承認の口: intake は下書きの題と本文の全文を投稿し、スレッドへの「公開 <番号>」を公開の依頼として、「取り消し <番号>」を下書きの破棄の依頼として、取り消しと同じファイルに書く（依頼に種類を足す）。orca は次の tick で読み、公開なら Issue を作る。下書きを捨てても規則は有効のまま。1 つの投稿に収まらない長い本文は省いて出し、その下書きは Slack からは公開できない（読んでいない文を承認させない）。端末では `status` が下書きの全文を出し、人のコマンド `orca-auto.ts learn-publish --name <名前> --rule <規則の id>` で公開できる（判定の AI には許さない）。
  - 公開のときに検査に落ちた下書き・取り下げた規則の下書きは捨てる。Issue を作れなかったら下書きを残し、次の依頼か tick でやり直す。
- 作る Issue には、Ready と管理の印（`slack-thread`）と、判定の改善であることを示すラベルを付ける。yui-cc-plugins を拾う元にしている `--auto` が、これを普通の Issue として拾う。
- orca は自分が作った改善の Issue の key を覚えておき、その Issue の PR ができたら（人の確認に回ったら）学びの出来事として知らせる。intake のステータスの知らせは、そのホームのリポジトリの Issue しか見ないため、それに頼らない。
- 判定の改善のラベルが付いた Issue の PR は、ほかの条件がそろっても AI が merge しない（理由の 1 行: 「判定の基準を変える PR は人が merge します」）。
- 「いいえ」の端末と権限の無い端末では、Issue を作らない。学びの知らせに「全体に効きそうな学び」として 1 行足すだけにする。

## 作る順番

1. 履歴・振り返り・規則・判定での使い方・様子見（orca だけで閉じる。知らせは tick の出力と `status`）。
2. Slack の知らせと取り消し（intake と orca）。
3. 全体に効く学び（setup の質問、改善の Issue、判定の改善の PR を AI が merge しない関門）。

各段の終わりで動く状態にする。

## 私が決めたこと（人が決めていない点）

- 食い違いの定義と、振り返りを起こす件数（3 件）。
- 様子見の件数（3 件）、有効な規則の上限（1 リポジトリ 20 件）、事例の件数（5 件）、履歴の上限（500 件）。
- 様子見の途中で失敗したら、その規則を取り下げる。
- 振り返りを、判定の AI の起動に相乗りさせる（新しい権限を足さない）。
- 知らせの投稿先は、intake の定期報告のチャンネル。
- 公開リポジトリに出す文の検査（リポジトリ名・`#数字`・URL を含まない）。
- 改善の Issue を公開する前に、人が Slack（または端末）で全文を読んで承認する段（実装の途中で、検査では言い換えや符号化した漏れを止められないと分かったため。人に尋ねたが返事が無く、漏れは取り消せないので安全側に倒した。全自動に戻すなら、下書きを作るところから公開を直接呼ぶ数行の直しで戻せる）。
- 判定の改善の PR は、必ず人が merge する。

## builder に任せること

- ファイルの名前と JSON の細かい形、定数の名前。
- 語の重なりの数え方（日本語の題名の区切り方を含む）。
- 判定結果のファイルに規則の案を足す形（今の配列の形を読める互換を保つこと）。
- 判定の改善を示すラベルの名前と、intake のラベルの一覧への足し方。
- 文書（両プラグインの SKILL.md・guide-ja.md・`auto-judge.md` と日本語版・README・CLAUDE.md）と版の上げ。
